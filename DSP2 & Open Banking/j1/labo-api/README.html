Labo — De l’API au consentement

Labo interactif du Jour 1 du cours DSP2 & Open Banking, à placer juste après la séquence S2 · La réponse. Trois temps de l’accès API : accorder un consentement, récupérer les comptes en JSON, puis révoquer l’accès.

Contexte

Lyam a un compte chez Banque Est. MonBuddy doit lire ses comptes. Dans le labo « Screen scraping », elle devait rejouer le mot de passe de Lyam et lire un tableau HTML : fragile et intrusif. Ici, Banque Est expose une API conforme DSP2 : plus de mot de passe, un consentement, un jeton, et une révocation possible à tout moment.

  • Étape 1 — Consentement : Lyam autorise MonBuddy, choisit les comptes et la durée ; la banque émet un consentId et un access_token.
  • Étape 2 — Appel API : MonBuddy appelle GET /accounts avec son jeton ; la banque répond du JSON structuré, pas du HTML à scraper.
  • Étape 3 — Révocation : Lyam révoque ; le jeton est invalidé immédiatement, le prochain appel reçoit 401.

Comment lancer (aucune installation)

Ce labo est 100 % autonome : pas de serveur, pas de dépendance, pas d’internet requis.

  1. Téléchargez (ou décompressez) le dossier labo-api/.
  2. Double-cliquez sur index.html.
  3. Le labo s’ouvre dans votre navigateur (Chrome, Firefox, Edge, Safari).
Astuce — si votre navigateur bloque quelque chose, ouvrez une fenêtre et glissez-déposez index.html dedans. La page fonctionne aussi bien en file:// qu’en ligne, car tout est côté client (JS pur).

Toutes les manipulations, une par une

Voici tout ce que vous pouvez faire dans le labo, classé par onglet. Chaque action indique ce qu’il faut observer.

Onglet 1 — Consentement

Action 1.1 — Accorder le consentement

  1. Sur l’onglet 1 · Consentement (affiché par défaut), cochez les comptes autorisés (par défaut : « Compte courant » et « Livret A »).
  2. Choisissez une durée (par défaut : 90 jours).
  3. Cliquez sur « Accorder le consentement ».

À observer :

  • La banque émet un consentId et un access_token.
  • Les scopes (comptes autorisés) et l’expiration sont affichés — l’accès est limité et daté.
  • Le mot de passe de Lyam n’apparaît nulle part : la banque ne l’a jamais partagé.

Action 1.2 — Révoquer depuis cet onglet (facultatif)

  • Cliquez sur « Révoquer maintenant » pour invalider le jeton immédiatement.

Onglet 2 — Appel API

Action 2.1 — Appeler /accounts

  1. Cliquez sur l’onglet 2 · Appel API.
  2. Cliquez sur « Appeler /accounts ».

À observer :

  • La requête GET /v1/accounts s’affiche avec l’en-tête Authorization: Bearer ….
  • La réponse JSON structurée apparaît : des champs nommés (accountId, iban, balance…), pas des balises à deviner.
  • Côté MonBuddy, les comptes reçus s’affichent lisiblement.
Stable par contrat — l’API est versionnée (/v1). Une refonte du site web ne casse rien ici, contrairement au scraping où un changement de classe CSS suffisait à tout casser.

Onglet 3 — Révocation

Action 3.1 — Révoquer puis réessayer

  1. Cliquez sur l’onglet 3 · Révocation.
  2. Cliquez sur « Révoquer le consentement ».
  3. Cliquez sur « Réessayer GET /accounts ».

À observer :

  • Le statut du consentement passe à « révoqué ».
  • La nouvelle tentative d’appel reçoit 401 Unauthorized : MonBuddy n’a plus aucun accès.
  • Lyam n’a pas eu à changer son mot de passe — c’est toute la différence avec le scraping.
Le pouvoir qui manquait au scraping — avec le scraping, MonBuddy avait le mot de passe : changer ce mot de passe ne la bloquait même pas, puisqu’elle l’avait stocké. Ici, la révocation est immédiate et certaine : le jeton ne vaut plus rien.

Navigation entre les onglets

  • Clic sur un onglet pour basculer.
  • Flèches ← / → au clavier pour passer d’un onglet à l’autre (accessibilité).

Exemple de réponse GET /accounts

La banque répond du JSON structuré, versionné par le contrat /v1 :

{ "data": [ { "accountId": "acc_1000", "type": "Compte courant", "iban": "FR76 3000 4000 0312 3456 7890 143", "currency": "EUR", "balance": "1 842,60 EUR" } ], "_links": { "self": "/v1/accounts" } }

Pistes de réflexion (pour l’atelier)

  1. Pourquoi un consentement vaut-il mieux qu’un couple identifiant / mot de passe ? (limité, daté, révocable)
  2. Pourquoi une réponse JSON est-elle plus stable qu’un tableau HTML à scraper ?
  3. Que se passe-t-il après révocation, et pourquoi Lyam n’a-t-il pas à changer son mot de passe ?
  4. Dans le scraping, MonBuddy pouvait-elle « révoquer » l’accès ? Que fallait-il faire, et suffisait-il ?
  5. En quoi ce labo illustre-t-il la réponse apportée par la DSP2 (séquence S2) ?

Fichiers

labo-api/ index.html → la page (point d'entrée, double-clic) labo-api.css → le style labo-api.js → toute la logique (onglets, consentement, appel, révocation) README.html → ce document (version lisible en navigateur)

Notes techniques

  • Aucune requête réseau : la « banque », l’API et l’« application » sont simulées dans la même page.
  • Aucun serveur : le consentement, le jeton et les réponses GET /accounts sont simulés en JavaScript pur.
  • Révocation : une fois le consentement révoqué, tout nouvel appel renvoie 401 Unauthorized, illustrant la perte immédiate d’accès.
  • Données fictives uniquement. Aucun identifiant réel, aucun compte réel.
