Atelier · De l’API au consentement

La S2 a montré la réponse : une API, un consentement, un jeton. Ici, on la manipule. Vous allez accorder le consentement de Lyam, récupérer ses comptes par un appel API en JSON, puis révoquer l’accès. Et vous verrez ce que le scraping ne savait pas faire : couper l’accès d’un clic.

Fil rouge

Vous êtes toujours l’équipe technique de MonBuddy. Mais cette fois, Banque Est a ouvert une API conforme DSP2. Plus besoin de mot de passe : Lyam autorise, MonBuddy reçoit un jeton, et l’accès peut être révoqué à tout moment.

Lancer le labo interactif

Cet atelier se fait dans un labo web autonome. Vous allez parcourir les trois temps de l’accès API : le consentement, l’appel, la révocation. Aucune installation, aucun serveur : un simple double-clic sur la page.

Ouvrir le labo ↗

Suivez la fiche ci-dessous en parallèle du labo : chaque étape indique ce qu’il faut observer à l’écran. Le dossier j1/labo-api/ est aussi distribuable tel quel aux étudiants (ouvrable par double-clic).

Objectif de l’atelier

Manipuler ce que la DSP2 change concrètement

Le scraping « marchait » mais ne savait ni limiter ni révoquer l’accès. L’atelier fait toucher du doigt les trois propriétés de la réponse API : un accès limité, des données structurées, un pouvoir de révocation.

Étape 1 · Consentir

Lyam autorise MonBuddy : choix des comptes, durée. La banque émet un consentId et un access_token.

Étape 2 · Appeler

MonBuddy appelle GET /accounts avec le jeton. La banque répond du JSON structuré, pas du HTML.

Étape 3 · Révoquer

Lyam révoque. Le jeton est invalidé immédiatement : le prochain appel de MonBuddy reçoit 401.

Étape 1 · consentement

Autoriser l’accès, c’est Lyam qui décide

Dans le labo, onglet « Consentement », cochez les comptes que Lyam autorise, choisissez une durée, puis cliquez sur « Accorder le consentement ». Observez ce que la banque renvoie.

  1. Accordez le consentement. Cochez « Compte courant » et « Livret A », gardez 90 jours, cliquez. Notez le consentId et le access_token émis.
  2. Repérez ce qui n’existe PAS. Aucun mot de passe n’apparaît. MonBuddy ne reçoit qu’un jeton limité aux comptes choisis et daté.
  3. Comparez avec le scraping. Dans l’atelier précédent, que MonBuddy stockait-il ? Pour combien de temps ? Était-ce limité à certains comptes ?

Ce que ça révèle déjà

Le consentement n’est pas un formulaire de plus : c’est un objet que la banque émet, horodate et limite. Il porte les droits, pas l’identité. C’est le contraire d’un mot de passe, qui donne accès à tout, indéfiniment.

Étape 2 · appel API

Récupérer les comptes en JSON structuré

Dans le labo, onglet « Appel API », cliquez sur « Appeler /accounts ». MonBuddy envoie son jeton en en-tête, la banque répond du JSON. 

GET /v1/accounts
Authorization: Bearer at_…  (jeton, PAS le mot de passe)

200 OK
{
  "data": [
    {
      "accountId": "acc_1000",
      "type": "Compte courant",
      "iban": "FR76 3000 4000 0312 3456 7890 143",
      "currency": "EUR",
      "balance": "1 842,60 EUR"
    }
  ]
}
  1. Lancez l’appel. Observez le JSON renvoyé : des champs nommés (balance, iban), pas des balises à deviner.
  2. Comparez avec l’extraction du scraping. Le robot lisait des td.montant fragiles. Ici, le champ balance est garanti par le contrat /v1.
  3. Imaginez une refonte. Si la banque refait son site web, l’API /v1 ne change pas. L’appel continue de fonctionner.

Stable par contrat

La version (/v1) est une promesse : les champs ne disparaissent pas dans ton dos. Une refonte graphique n’est pas une rupture d’API. C’est toute la différence avec le scraping, où chaque changement de classe CSS casse le robot.

Étape 3 · révocation

Couper l’accès, d’un clic

Dans le labo, onglet « Révocation », cliquez sur « Révoquer le consentement », puis sur « Réessayer GET /accounts ». Observez la réponse de la banque.

  1. Révoquez. Le statut passe à « révoqué » et le jeton est invalidé immédiatement.
  2. Réessayez l’appel. MonBuddy reçoit 401 Unauthorized : plus aucun accès.
  3. Comparez avec le scraping. Dans l’atelier précédent, Lyam pouvait-il « révoquer » MonBuddy ? Que fallait-il faire — et cela suffisait-il ?

Le pouvoir qui manquait au scraping

Avec le scraping, MonBuddy avait le mot de passe. Changer ce mot de passe ne la bloquait même pas : elle l’avait stocké. Ici, la révocation est immédiate et certaine : le jeton ne vaut plus rien. C’est ce pouvoir de reprise de contrôle que la DSP2 garantit.

Débrief · 5 min

Scraping vs API : ce qui change vraiment

Reprenez les trois étapes et complétez la comparaison. C’est la synthèse de S2, vue par la pratique.

Scraping (atelier précédent)

  • MonBuddy stocke le mot de passe.
  • Accès à tout le compte, sans limite.
  • Lecture de balises fragiles.
  • Aucune révocation possible.

API + consentement (cet atelier)

  • MonBuddy reçoit un jeton, jamais le mot de passe.
  • Accès limité aux comptes + une durée.
  • Données JSON structurées et versionnées.
  • Révocation immédiate du jeton.

Le message de l’atelier. La DSP2 ne rend pas le service « plus joli » : elle rend l’accès limité, structuré et révocable. Le scraping empruntait une interface faite pour les humains. L’API prête une interface faite pour les applications — avec un contrat et une poignée de main consentie.
