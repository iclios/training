Les briques exposées

Architecture API

Une API Open Banking n’est pas un seul service : c’est un ensemble de types d’API spécialisés, exposés derrière des composants qui en assurent l’accès, le contrôle et la traçabilité.

Fil rouge

L’application de Léa n’utilise pas « une API » : elle appelle une API de lecture de comptes. Demain, si Léa paie un marchand par virement, elle utilisera une API d’initiation de paiement. Ce ne sont pas les mêmes services.

Types

Les trois types d’API

La DSP2 définit trois familles de services qui correspondent à trois types d’API. Chacune a un périmètre strict.

Account Information API

Lecture des comptes · AIS

Expose soldes, opérations et détails de comptes à un AISP. Lecture seule : aucun mouvement de fonds n’est possible.

Cours — périmètre

Endpoints typiques : liste des comptes, détail d’un compte, liste des transactions, solde. Accès conditionné par un consentement AIS et une SCA initiale.

Payment Initiation API

Initiation de paiement · PIS

Permet à un PISP de déclencher un virement au nom du client, sans jamais détenir les fonds.

Cours — périmètre

Endpoints : création d’une demande de paiement, statut du paiement. Chaque paiement est authentifié par une SCA ; le montant et le bénéficiaire ne peuvent plus être modifiés après la SCA.

Confirmation of Funds API

Vérification de fonds · CBPII

Permet à un CBPII de savoir si des fonds sont disponibles sur un compte, sans exposer les soldes.

Cours — périmètre

Réponse binaire : « fonds suffisants » ou non, pour un montant donné. Aucune donnée de solde ni d’opération n’est renvoyée.

Une API, un usage

Une banque peut exposer les trois types, mais un TPP n’accède qu’aux types couverts par son agrément. Un AISP n’obtient jamais le droit d’appeler l’API de paiement : la séparation est technique et réglementaire.

Composants

Les composants qui exposent l’API

Derrière chaque type d’API, une même infrastructure. On retrouve ici les couches du Jour 1, vues cette fois du côté de l’exposition.

De l’appel TPP au service métier

Les composants d’exposition de l’API

1
API Gateway

Point d’entrée unique. Termine le chiffrement, vérifie le certificat du TPP (mTLS), route vers le bon service et rejette les appels malformés ou abusifs.

2
API Management

Gère le catalogue d’API, les quotas par TPP, le throttling (limitation de débit) et le versionnement. C’est l’endroit où l’on décide qui a le droit d’appeler quoi, à quelle fréquence.

3
Services API métier

Implémentent réellement AIS, PIS, CBPII : vérification du consentement, contrôle du périmètre, validation des règles métier avant d’appeler le core banking.

4
Logs & traçabilité

Chaque appel est journalisé : qui (TPP), quoi (endpoint), quand (horodatage), résultat (code), et combien de temps. Indispensable à l’audit, aux litiges et au monitoring.

Throttling : pourquoi c’est une exigence, pas une option

Les RTS imposent des plafonds de consultation. Sans limitation de débit, un TPP mal codé peut saturer l’API et faire tomber, pour tous les autres, l’accès aux comptes. Le throttling protège la disponibilité du service — donc la qualité pour Léa.

Séquence suivante

Mais qui a le droit d’appeler ?

On a les briques et les composants. Reste la question centrale : comment prouve-t-on qu’un appel vient bien d’un TPP agréé, au nom d’un client qui a consenti ? C’est tout l’objet de l’authentification et de l’autorisation (S2).

Cours — récapitulatif du bloc
  • Trois types d’API : AIS (lecture), PIS (paiement), CBPII (vérification de fonds).
  • Composants : Gateway (entrée), API Management (quotas, throttling, versionnement), Services métier, Logs.
  • Principe : un seul type par agrément, séparation technique et réglementaire.

Points de sortie de S1

  • Je nomme les trois types d’API et leur périmètre.
  • Je distingue Gateway et API Management.
  • Je sais pourquoi le throttling est obligatoire.
  • Je comprends ce que doit contenir un log d’appel.
