Accueil

Intro & objectifs

Le Jour 1 a posé le pourquoi et le qui. Le Jour 2 passe au comment technique : de quoi est faite une API bancaire, par quels mécanismes un tiers est autorisé, et comment l’ensemble reste sûr et conforme.

Fil rouge

Samedi, 9 h 12. L’application de Lyam prépare sa requête. Elle doit prouver qui elle est (le TPP), obtenir une autorisation (le consentement de Lyam), puis présenter un jeton à chaque appel. Le Jour 2 ouvre ce capot.

Rappel

Ce que l’on a fixé au Jour 1

DSP2 = Deuxième Directive sur les Services de Paiement (directive (UE) 2015/2366). Open Banking = l’ouverture des données de compte et des paiements à des tiers agréés, avec le consentement du client. La DSP2 est la règle, l’Open Banking la pratique, et l’API en est l’outil technique — celui que l’on étudie aujourd’hui.

Le fil conducteur du Jour 2

Une API Open Banking protège trois choses en même temps : l’identité du tiers, l’autorisation du client et l’intégrité de chaque appel. Chaque bloc du jour correspond à l’une de ces protections.

Aperçu

Le parcours du Jour 2, en une image

Quatre séquences, du composant au cas concret. On part de la brique API, on monte jusqu’aux mécanismes d’authentification, puis aux exigences de sécurité, pour finir par une mise en situation complète.

02 · S1 · Architecture API

S1 · Architecture API

Jour 2 · Séquence 1 35 min

Une infrastructure, trois services

Architecture API — le socle commun

AIS, PIS, CBPII : trois API aux usages différents, mais bâties sur la même infrastructure d’exposition. On commence par ce socle commun — passerelle, gestion, services, journalisation — avant de détailler chaque API dans les séquences suivantes.

Fil rouge

L’application de Lyam n’utilise pas « une API » : elle appelle une API de lecture de comptes (AIS). Demain, si Lyam paie un marchand par virement, ce sera une API d’initiation de paiement (PIS). Derrière ces appels différents, la banque expose toujours la même plomberie : c’est ce socle qu’on découvre ici.

Orientation

Trois API, un même socle

La DSP2 définit trois familles de services, chacune exposée par une API dédiée. Leur logique métier diffère ; leur infrastructure d’exposition est commune. Cette séquence pose le socle ; les deux suivantes détaillent le workflow propre à l’AIS et au CBPII. Le PIS, lui, fait l’objet du Jour 3.

Account Information API

Lecture des comptes · AIS

Lit soldes, opérations et détails de comptes. Lecture seule, aucun mouvement de fonds.

→ S2 · détail de l’API AIS

Payment Initiation API

Initiation de paiement · PIS

Déclenche un virement au nom du client, sans jamais détenir les fonds.

→ détaillé au Jour 3

Confirmation of Funds API

Vérification de fonds · CBPII

Répond « fonds disponibles ? » sans exposer de solde.

→ S3 · workflow CBPII

Une API, un usage

Une banque peut exposer les trois types, mais un TPP n’accède qu’aux types couverts par son agrément. Un AISP n’obtient jamais le droit d’appeler l’API de paiement : la séparation est technique et réglementaire.

Composants

Les composants qui exposent l’API

Quelle que soit l’API appelée, l’appel traverse la même chaîne de composants. On retrouve ici les couches du Jour 1, vues cette fois du côté de l’exposition.

De l’appel TPP au service métier

Les composants d’exposition de l’API

1
API Gateway

Point d’entrée unique. Termine le chiffrement, vérifie le certificat du TPP (mTLS), route vers le bon service et rejette les appels malformés ou abusifs.

2
API Management

Gère le catalogue d’API, les quotas par TPP, le throttling (limitation de débit) et le versionnement. C’est l’endroit où l’on décide qui a le droit d’appeler quoi, à quelle fréquence.

3
Services API métier

Implémentent réellement AIS, PIS, CBPII : vérification du consentement, contrôle du périmètre, validation des règles métier avant d’appeler le core banking. C’est ici que chaque API devient différente (S2 AIS, S3 CBPII).

4
Logs & traçabilité

Chaque appel est journalisé : qui (TPP), quoi (endpoint), quand (horodatage), résultat (code), et combien de temps. Indispensable à l’audit, aux litiges et au monitoring.

Throttling : pourquoi c’est une exigence, pas une option

Les RTS imposent des plafonds de consultation. Sans limitation de débit, un TPP mal codé peut saturer l’API et faire tomber, pour tous les autres, l’accès aux comptes. Le throttling protège la disponibilité du service — donc la qualité pour Lyam.

Séquence suivante

Maintenant, chaque API en détail

Le socle est posé. On peut désormais spécialiser : chaque API a son cœur métier, ses endpoints, ses règles SCA et ses risques propres. Commençons par la plus utilisée : la lecture de comptes (S2 · AIS).

Cours — récapitulatif du bloc
  • Trois API, un socle : AIS (lecture), PIS (paiement), CBPII (fonds) partagent la même infrastructure d’exposition.
  • Composants : Gateway (entrée), API Management (quotas, throttling, versionnement), Services métier, Logs.
  • Point de divergence : c’est dans les services métier que chaque API devient spécifique (workflow AIS en S2, CBPII en S3 ; PIS au Jour 3).
  • Principe : un seul type par agrément, séparation technique et réglementaire.
Références — RTS EBA 2018/389 (interfaces dédiées, limites de performance) ; orientations EBA sur les interfaces dédiées ; Berlin Group NextGenPSD2 (structures AIS/PIS/CBPII).

03 · S2 · Workflow AIS

S2 · Workflow AIS

Jour 2 · Séquence 2 30 min

Lire les comptes, jamais les toucher

Workflow AIS — Account Information

L’API que Lyam utilise au quotidien : lire ses soldes et ses opérations depuis son application. Sur le socle de S1, elle ajoute un cœur métier précis : lecture seule, cadrée par un consentement et une authentification forte initiale.

Fil rouge

Lyam ouvre son application de gestion de budget. Elle affiche la liste de ses comptes, le solde de chacun et ses dernières opérations. Pour cela, elle appelle l’API AIS de Banque Est avec le consentement que Lyam a donné une fois — et qui reste valable jusqu’à 90 jours.

Cœur métier

Ce que fait — et ne fait pas — l’API AIS

Ce qu’elle fait

  • Lister les comptes (comptes courants, livrets, cartes)
  • Donner le détail d’un compte (IBAN, titulaire, type)
  • Lister les transactions d’un compte, filtrables par date
  • Donner les soldes (comptabilisé, disponible)

Ce qu’elle ne fait jamais

  • Aucun mouvement de fonds (pas de virement, pas de prélèvement)
  • Aucune modification du compte
  • Aucun accès sans consentement AIS actif
  • Aucun accès aux comptes non couverts par le consentement

Le principe

L’AISP lit ; il ne touche à rien. Le risque de l’AIS n’est pas la fraude financière, c’est la confidentialité des données de comptes.

Parcours

Le parcours d’une lecture de comptes

Une lecture AIS suit toujours la même séquence : consentement, authentification forte initiale, puis lecture répétée tant que le consentement est valide.

Flux d’une lecture AIS

Consentement → SCA initiale → lectures → révocation

1
Création du consentement

L’AISP déclare au nom de Lyam ce qu’il veut lire (comptes, transactions, soldes) et pour combien de temps. La banque renvoie un identifiant de consentement.

2
SCA initiale

Lyam s’authentifie fortement (deux facteurs) auprès de sa banque et autorise explicitement le consentement. C’est le seul moment où il prouve son identité.

3
Lecture répétée

Avec un jeton d’accès, l’AISP lit les comptes et les transactions. Plus de SCA à chaque lecture : l’accès reste ouvert jusqu’à expiration du consentement (max 90 jours sous RTS).

4
Révocation

Lyam peut révoquer le consentement à tout moment. L’accès est coupé immédiatement, quelles que soient les jetons en circulation.

Étape Endpoint typique (Berlin Group) But
ConsentementPOST /v1/consentsDéclarer le périmètre et la durée
ComptesGET /v1/accountsLister les comptes autorisés
DétailGET /v1/accounts/{accountId}IBAN, titulaire, type
SoldesGET /v1/accounts/{accountId}/balancesSolde comptabilisé / disponible
TransactionsGET /v1/accounts/{accountId}/transactionsOpérations, filtrables par date

Les noms exacts varient selon le standard (Berlin Group, STET, OBIE). Ce qui est normalisé par la DSP2, c’est le service rendu, pas l’URL.

Données

À quoi ressemble une réponse AIS

L’AIS renvoie des données riches — c’est justement ce qui le rend sensible. Exemple simplifié d’une réponse « transactions » : 

{
  "account": { "iban": "FR76…1234" },
  "transactions": {
    "booked": [
      {
        "transactionId": "TX-2025-0001",
        "bookingDate": "2025-11-08",
        "amount": { "currency": "EUR", "amount": "-42.90" },
        "creditorName": "SNCF",
        "remittanceInformation": "Billet Paris–Lyon"
      },
      {
        "transactionId": "TX-2025-0002",
        "bookingDate": "2025-11-07",
        "amount": { "currency": "EUR", "amount": "2500.00" },
        "debtorName": "ACME SARL",
        "remittanceInformation": "Salaire novembre"
      }
    ]
  }
}

Pourquoi c’est sensible

Une réponse AIS révèle les revenus, les habitudes d’achat, les bénéficiaires, la santé financière de Lyam. C’est une donnée personnelle au sens du RGPD : d’où le consentement explicite, la durée bornée et le droit de révocation à tout moment.

Risques

Les erreurs et risques propres à l’AIS

Code HTTP Signification Ce que fait l’AISP

Le piège : le stockage des données

L’AISP ne doit conserver les données lues que pour la durée strictement nécessaire au service rendu. Un AISP qui garde une copie intégrale des transactions « au cas où » sort de son cadre — et s’expose au RGPD comme à la DSP2.

Séquence suivante

Et si l’on ne faisait que vérifier ?

L’AIS lit beaucoup. La troisième API, elle, répond à une seule question — « y a-t-il assez de fonds ? » — sans révéler de solde. C’est un tout autre workflow, minimaliste par choix (S3 · CBPII).

Cours — récapitulatif du bloc
  • Rôle : lecture seule des comptes, soldes et transactions.
  • Parcours : consentement → SCA initiale → lecture répétée → révocation.
  • Durée : consentement valable jusqu’à 90 jours (RTS), une seule SCA initiale.
  • Risque : confidentialité des données (revenus, habitudes), conformité RGPD.
Références — RTS EBA 2018/389 (art. 10, accès fréquents ; validité du consentement) ; Berlin Group NextGenPSD2 (AIS) ; RGPD (art. 5, 6, 17).

04 · S3 · Workflow CBPII

S3 · Workflow CBPII

Jour 2 · Séquence 3 25 min

Une seule question, une seule réponse

Workflow CBPII — Confirmation of Funds

La plus discrète des trois API : elle répond à une unique question — « y a-t-il assez de fonds pour ce montant ? » — par un simple oui ou non, sans jamais révéler de solde ni d’opération.

Fil rouge

Lyam a une carte de paiement adossée à un porte-monnaie géré par un émetteur. Avant d’autoriser une dépense, l’émetteur demande à Banque Est : « le compte de Lyam couvre-t-il 42,90 € ? ». Réponse : oui ou non. L’émetteur n’apprend ni le solde, ni les opérations de Lyam.

Cœur métier

Une API volontairement pauvre

Là où l’AIS expose des données riches, le CBPII expose le minimum nécessaire. C’est un choix de conception protecteur : moins de données exposées, moins de risque.

Ce qu’elle fait

  • Répond oui/non à « fonds suffisants pour tel montant ? »
  • Se limite au compte et au montant demandés
  • Sert de contrôle avant une autorisation de paiement

Ce qu’elle ne fait jamais

  • Renvoyer un solde (même approximatif)
  • Lister des transactions
  • Déplacer des fonds
  • Donner des informations sur d’autres comptes

Le principe

Le CBPII ne lit pas : il vérifie. Une réponse binaire vaut mieux qu’un solde exposé — c’est la protection par la pauvreté de la donnée.

Parcours

Le parcours d’une vérification de fonds

Flux d’une vérification CBPII

Consentement → SCA initiale → vérifications → révocation

1
Consentement CBPII

Le CBPII obtient le droit de vérifier les fonds d’un compte donné pour un usage défini. Le consentement précise le compte et la finalité.

2
SCA initiale

Comme pour l’AIS, une authentification forte initiale est requise pour établir le consentement. Le CBPII ne s’authentifie pas à chaque vérification.

3
Vérification répétée

Pour chaque dépense, le CBPII envoie le montant et reçoit un booléen. La fréquence est bornée par les RTS (pas d’interrogation abusive du solde par ce biais).

4
Révocation

Lyam peut retirer le consentement ; le CBPII perd alors toute possibilité de vérifier les fonds.

Étape Endpoint typique (Berlin Group) But
ConsentementPOST /v1/funds-confirmationsDéclarer le compte à vérifier
Vérificationappel avec montant + compteObtenir « fonds suffisants : oui/non »

Données

À quoi ressemble une réponse CBPII

La réponse est minimale. Pas de montant de solde, pas de transaction : un seul indicateur booléen. 

{
  "fundsAvailable": true,
  "account": { "iban": "FR76…1234" }
}

Un booléen, pas un solde

Pourquoi ne pas simplement renvoyer le solde ? Parce que le solde est une donnée sensible. Le CBPII n’a besoin que de la réponse à sa question : le minimum exposé est le maximum protégé.

Usages

Cas d’usage et limites

Cas d’usage Intérêt du CBPII
Porte-monnaie / carte prépayéeVérifier la couverture avant d’autoriser
Émetteur de carteContrôle de solvabilité sans voir les comptes
Paiement en plusieurs foisS’assurer de la capacité de remboursement

Le piège : l’interrogation abusive

Multiplier les vérifications permet de reconstituer un solde par déduction. Les RTS limitent donc la fréquence d’interrogation — c’est le même enjeu de throttling vu en S1, mais ici pour protéger une donnée déduite, pas un service.

Cours — récapitulatif du bloc
  • Rôle : répondre oui/non à « fonds suffisants pour ce montant ? ».
  • Minimalisme : jamais de solde, jamais de transactions.
  • Parcours : consentement → SCA initiale → vérifications répétées → révocation.
  • Risque : reconstitution du solde par interrogation répétée (bornée par les RTS).
Références — DSP2 (art. 65, confirmation de fonds) ; RTS EBA 2018/389 (fréquence d’interrogation) ; Berlin Group NextGenPSD2 (confirmation of funds).

05 · S5 · Authentification & autorisation

S5 · Authentification & autorisation

Jour 2 · Séquence 5 55 min

Qui prouve quoi, et jusqu’où

Authentification & autorisation

Quatre mécanismes reviennent sans cesse en Open Banking : OAuth2, OpenID Connect, mTLS et JWT. Chacun répond à une question différente. Les confondre, c’est ouvrir une faille.

Fil rouge

Quand l’application de Lyam appelle Banque Est, trois choses doivent être vraies : l’appel vient d’un TPP agréé, Lyam s’est authentifiée, et l’accès demandé est bien couvert par son consentement. Un seul mécanisme ne suffit pas.

Mécanismes

Les quatre mécanismes clés

OAuth2

Authorization Framework

Cadre d’autorisation. Il permet à un TPP d’obtenir un jeton d’accès sans jamais connaître les identifiants de Lyam.

Cours — à retenir

OAuth2 n’authentifie pas : il autorise. Flux clé en Open Banking : le code d’autorisation avec redirection. Le TPP reçoit un code, l’échange contre un jeton.

OpenID Connect

Couche d’identité sur OAuth2

Ajoute l’identité à OAuth2 : un ID token (JWT) qui atteste qui est l’utilisateur authentifié.

Cours — à retenir

OIDC répond à « qui est cet utilisateur ? », là où OAuth2 répond à « à quoi a-t-il droit ? ». En Open Banking, l’ID token prouve l’identité de Lyam côté TPP.

mTLS

Mutual TLS

Authentification mutuelle par certificat. Le TPP et la banque se présentent chacun un certificat : chacun prouve son identité à l’autre.

Cours — à retenir

mTLS est la preuve que le TPP est bien le TPP agréé, au niveau du canal. Le certificat est lié à l’agrément (registre EBA) : c’est un contrôle d’identité technique.

JWT

JSON Web Token

Format de jeton signé. Il transporte des affirmations (scopes, expiration, émetteur) vérifiables sans rappeler le serveur à chaque fois.

Cours — à retenir

Un JWT est signé, pas chiffré : on peut le lire. Il ne doit donc jamais contenir de données sensibles. Sa signature garantit qu’il n’a pas été modifié.

Mécanisme Répond à la question Niveau
mTLSLe TPP est-il bien celui qu’il prétend ?Canal
OAuth2À quoi le TPP a-t-il droit ?Autorisation
OpenID ConnectQui est l’utilisateur authentifié ?Identité
JWTComment transporter la preuve, signée ?Jeton

Le point clé

Trois authentifications, trois autorisations

Il faut bien séparer trois notions distinctes, que l’on ne doit jamais fusionner.

Identification du client

Lyam prouve qui il est auprès de sa banque (SCA). C’est lui, physiquement et juridiquement, qui est à l’origine de la demande.

Identification du TPP

L’application prouve qu’elle est un TPP agréé (certificat, agrément). C’est une identité technique, liée au registre EBA.

Autorisation d’accès

Le périmètre concédé à ce client et à ce TPP : quels comptes, quelles opérations, jusqu’à quand. C’est le consentement, matérialisé en jetons.

Ne jamais faire l’impasse sur une des trois

Un TPP valide qui accède au compte d’un client qui n’a pas consenti = faille. Un client authentifié dont le TPP n’est pas agréé = faille. Un consentement large exploité par un TPP malveillant = faille. Les trois contrôles sont indépendants et tous nécessaires.

Règle à retenir

Authentifier le client ≠ authentifier le TPP ≠ autoriser l’accès aux données. Ces trois vérifications se font à des endroits différents de la chaîne, avec des mécanismes différents.

Flux

Le flux OAuth2 en Open Banking

Le parcours de redirection du Jour 1, vu cette fois avec les jetons et les contrôles.

Cliquez pour suivre les étapes

Deux jetons, deux rôles

L’access token est court (quelques minutes à quelques heures) et porte les scopes. Le refresh token sert à en obtenir un nouveau sans redemander la SCA — dans les limites du consentement et des règles d’authentification. Ne jamais confondre leur durée de vie.

Séquence suivante

Et les obligations réglementaires ?

Les mécanismes techniques sont posés. Mais la DSP2 impose des exigences précises : SCA, exemptions, non-répudiation, horodatage. Et l’industrialisation de ces flux expose à des risques : usurpation, attaques API, fuites. C’est la S6.

Références — RFC 6749 (OAuth2), RFC 7519 (JWT), OpenID Connect Core ; RTS EBA 2018/389, art. 28-30 (communication sécurisée, interfaces dédiées).

06 · S6 · Sécurité & conformité

S6 · Sécurité & conformité

Jour 2 · Séquence 6 50 min

Exigences DSP2 et risques API

Sécurité & conformité

La DSP2 ne dit pas seulement « protégez » : elle impose des mécanismes précis (SCA, exemptions, non-répudiation, horodatage) et laisse aux banques la responsabilité de tenir leurs APIs contre des menaces concrètes.

Fil rouge

Lyam s’est authentifiée et l’application a son jeton. Mais que se passe-t-il si quelqu’un usurpe le TPP ? Si un appel est rejoué ? Si des données fuitent ? Cette séquence répond à ces menaces.

SCA

La Strong Customer Authentication

La SCA (authentification forte du client) exige au moins deux facteurs indépendants parmi trois catégories : connaissance (mot de passe, code), possession (téléphone, token), inhérence (empreinte, visage). Les deux facteurs doivent être de catégories différentes et leur compromission isolée ne doit pas suffire à contourner l’authentification.

Connaissance

Quelque chose que Lyam sait : mot de passe, code PIN.

Possession

Quelque chose que Lyam possède : son téléphone, une carte.

Inhérence

Quelque chose que Lyam est : empreinte digitale, reconnaissance faciale.

Quand la SCA s’applique

À l’accès initial aux comptes (AIS), puis lors des re-authentifications périodiques (au moins tous les 90 jours en AIS), et à chaque paiement initié par un PISP, sauf exemption applicable. Deux mots de passe ne font pas une SCA : il faut deux catégories différentes.

Exemptions

Les exemptions à la SCA

La SCA systématique serait insupportable pour le client. Les RTS prévoient des exemptions, mais chacune est bornée et surveillée (fraude). La banque doit pouvoir justifier leur usage.

Exemption Principe Garde-fou
Faible montant Paiements de faible valeur sous un plafond Compteur (nombre / cumul sur une période)

Exemption ≠ absence de contrôle

Une exemption ne supprime pas la vérification : elle déplace la SCA à un autre moment (création du bénéficiaire, re-authentification périodique) et s’accompagne d’une surveillance de la fraude. Abuser d’une exemption entraîne son retrait.

Preuve

Non-répudiation et horodatage

Non-répudiation

La banque doit pouvoir prouver qu’un paiement ou un accès a bien eu lieu et dans quelles conditions : qui, quel montant, quel bénéficiaire, à quel moment. Un client ne doit pas pouvoir nier un paiement qu’il a autorisé, et le TPP ne doit pas pouvoir contester un appel reçu.

Horodatage

Chaque événement porte une date et heure de référence fiable, conservée et cohérente entre les acteurs. C’est la base du contrôle : durée de validité d’un jeton, période de consentement, décompte des exemptions.

Ce que cela impose techniquement

Journalisation horodatée de chaque appel (requête/réponse), signature des messages pour garantir leur intégrité et leur origine (non-répudiation), conservation conforme aux délais légaux. Sans ces preuves, un litige ne peut être tranché.

Risques

Trois familles de risques API

Usurpation d’identité

Un attaquant se fait passer pour un TPP agréé ou pour le client.

Contre-mesures : mTLS strict, vérification du registre EBA, contrôle de cohérence certificat/agrément, SCA robuste.

Attaques API

Rejeu de requêtes, injection, déni de service, abus de quota.

Contre-mesures : anti-rejeu (nonce, horodatage), validation des entrées, throttling, quotas par TPP, surveillance d’anomalies.

Fuites de données

Exposition de soldes ou d’opérations au-delà du périmètre consenti, ou interception.

Contre-mesures : scopes minimaux, chiffrement en transit, contrôle de périmètre à chaque appel, pas de données sensibles dans les JWT.

Banque Est doit ouvrir une API à un TPP de bout en bout. À vous de produire le schéma d’architecture, le flux OAuth et les points de contrôle de sécurité.

Fil rouge

L’application de Lyam (« FinanceApp ») demande à Banque Est un accès en lecture à ses deux comptes. Vous êtes l’équipe technique de Banque Est : il faut le brancher proprement — et en sécurité.

Énoncé

Le cas

FinanceApp est un AISP agréé. Banque Est doit lui ouvrir un accès en lecture aux comptes d’un client qui l’a autorisé, via une API Open Banking, en respectant les exigences du Jour 2.

Ce qu’il faut produire
