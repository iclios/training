JOUR 3 — Network tokenization & lifecycle

Objectif
Cycle du token (≠ carte) + ce qui circule en Auth (token chez l’acquéreur).

Parcours (UNE seule carte des états)
Provision → Actif → Suspend → Delete
Durée = états (longue) · crypto txn = éphémère
Détail actions = section Gouvernance (pas de doublon)

1 · Provisioning
Demande → contrôles issuer/TSP → token + domaine → vault

2 · Stockage dual (pas de 2e cycle de vie ici)
- Vault TSP : PAN ↔ token · état · gouvernance
- Credential : SE device / wallet / COF marchand
POS / app / acquéreur ≠ vault

3 · Auth — qui voit quoi
Device → Acceptation → Acquéreur → Réseau/TSP → Issuer
- Jusqu’à l’acquéreur inclus : TOKEN (+ crypto)
- TSP : détokenise token → PAN (vault)
- Issuer : décide sur le compte
Réponse salle : chez l’acquéreur = TOKEN, pas le PAN

Nuance
- Network tokenization (VTS/MDES) : token va jusqu’à l’acquéreur
- Vault marchand/PSP seul : PSP peut détokeniser et envoyer le PAN à l’acquéreur

4 · Gouvernance (détail unique des états)
Activate · Suspend · Delete — ciblé device/canal, carte intacte

5 · Cryptogramme
Token durable ≠ crypto dynamique anti-replay (pont J4)

Cas
Device perdu · nouveau device · « chez l’acquéreur ? » · carte réémise

Clarifications
Lifecycle ≠ carte · token ≠ crypto · vault ≠ credential ·
acquéreur ≠ PAN (network) · ≠ SE/HCE (J4)
