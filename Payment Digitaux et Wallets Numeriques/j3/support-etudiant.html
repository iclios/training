Jour 3 · Tokenisation

3.1 · Tokenisation

Définition

Définition monétique

Qu’est-ce que la tokenisation ?

Substitution du PAN par un token utilisable dans un domaine d’usage défini, gouverné par une infrastructure dédiée (vault / TSP), afin de réduire l’exposition des données carte sans changer la logique monétique Auth → Clearing → Settlement.

On sécurise l’identifiant présenté — pas le rail de paiement.

Vocabulaire

Deux identifiants

Deux numéros qui se ressemblent souvent à l’œil — ce n’est pas la même chose.

Carte plastique

PAN

PAN — Primary Account Number : numéro de compte carte (souvent 16 chiffres), imprimé ou embossé. Identifiant d’origine, sensible.

4532 1488 0342 7764

Wallet / device

Token

Token : substitut du PAN, émis pour un domaine (device, canal, marchand). Souvent même format — ce n’est pas le numéro de la carte.

4895 3702 1148 0091

Exemples pédagogiques uniquement. Le PAN reste la racine chez l’émetteur / le vault ; le canal (POS, app) voit le token.

Substitution illustrée

PAN sensible · Token gouverné · Domaine d’usage

Vocabulaire

Vault & TSP

Deux briques à ne pas confondre : le vault stocke le lien ; le TSP gouverne le cycle de vie.

Token vault

  • Référentiel sécurisé PAN ↔ token
  • Où vit la correspondance (pas le canal)
  • « Coffre » du mapping — pas l’acteur métier

TSP

  • Token Service Provider
  • Émet, active, suspend, supprime
  • Applique règles de domaine / device
  • Souvent scheme, parfois issuer ou acteur dédié

Lien PAN ↔ token

Vault = stockage · TSP = gouvernance

Où dans la chaîne ?

  • Vault / TSP : côté réseau / scheme (souvent) — pas dans la caisse ni l’app marchande
  • L’émetteur garde le PAN et la décision AuthZ — le TSP ne le remplace pas

Chaîne SI détaillée : Architecture SI · Qui voit token / PAN en Auth : Lifecycle · Auth

Émission

Comment naît le token (côté UX)

Le token est émis par un TSP après enrôlement — pas « calibré » localement. Le flux technique complet est dans Lifecycle · Provisioning ; ici, l’angle Définition : ce que voit l’utilisateur vs la coulisse.

Côté UX — enrôlement implicite

Geste simple · provisioning complet en coulisse

Clarification

À ne pas confondre

Tronquer et masquer se ressemblent à l’œil — ce n’est pas la même opération. Et aucun des deux n’est un token.

PAN tronqué · PAN masqué · Token

Tronquer = stocker moins · Masquer = afficher moins · Token = autre identifiant

≠ Chiffrement simple

Un token n’est pas un PAN chiffré affiché autrement : il a un domaine et une gouvernance.

≠ Nouveau rail

Auth → Clearing → Settlement reste intact. On change l’identifiant exposé, pas la logique monétique.

≠ Risque zéro

Exposition réduite — fraude, device et conformité restent des sujets SI.

Suite : Pourquoi tokeniser · Domaines d’usage · Lifecycle · Provisioning.

Jour 3 · Tokenisation

3.1 · Tokenisation

Objectifs de la tokenisation

Rôle

Pourquoi tokeniser

On ne change pas le rail Auth → Clearing → Settlement : on change ce qui est présenté — pour réduire l’exposition, la fraude réutilisable et le scope PCI.

Trois raisons

Ce que la tokenisation vise

1 · Moins d’exposition du PAN

  • Le canal voit un substitut, pas le numéro de carte
  • Le PAN reste chez l’émetteur / vault / TSP
  • Moins de copies dans POS, apps, logs, bases marchandes

2 · Fraude plus difficile à réutiliser

  • Token souvent lié à un domaine (device, canal, marchand)
  • Suspendre un token ≠ bloquer toute la carte
  • Ex. : téléphone perdu → revoke ciblé

3 · Conformité (PCI-DSS)

  • Moins de PAN côté marchand → scope PCI réduit — détail réglementaire : Sécurité & conformité

Contexte

Pourquoi surtout en digital ?

Le rail carte classique expose peu de copies persistantes ; les canaux digitaux multiplient stockage et acteurs.

Rail classique vs canaux digitaux

Où le token devient le modèle par défaut

Synthèse

Réduit · conserve · déplace

Effet
Réduit Copies du PAN dans POS, apps, logs, bases marchandes
Conserve Rail Auth → Clearing → Settlement (J1) · décision chez l’issuer
Déplace Gouvernance du mapping vers vault / TSP · responsabilité concentrée

Scope PCI réduit côté marchand ≠ disparition des contrôles (détail : 3.4).

3.1 · Tokenisation

Domaines d’usage

Modes / domaines

Où on tokenise

Un token n’est pas universel : il est émis pour un domaine (canal, device, parfois marchand). Même rail Auth → Clearing → Settlement — ce qui change, c’est qui tokenise, où vit le token et ce qui circule.

Vue d’ensemble

Trois terrains

In-store · In-app · E-commerce

In-store

Tap au POS

Le payeur ne tape pas son PAN : le device présente un token lié à l’appareil.

Domaine device → POS → Auth

Token device-bound · PAN hors POS

In-app

Checkout natif

L’achat se fait dans l’application du marchand — token wallet ou vault PSP, pas une WebView.

App → SDK / wallet → Backend → Auth

Deux variantes de tokenisation à distinguer

E-commerce

Card-on-file

Le marchand réutilise la carte (1-clic, abonnement) en stockant un token — pas le PAN.

Checkout → PSP / TSP → Marchand → MIT

COF + récurrence · cœur du scope PCI

Synthèse

Trois terrains · qui tokenise

In-store In-app E-commerce / COF
Qui tokenise TSP réseau (VTS · MDES · wallet OEM) TSP / wallet OEM PSP / TSP card-on-file
Où vit le mapping Vault TSP / scheme Vault TSP · device Vault PSP / TSP
En Auth circule TOKEN (+ crypto) jusqu’à l’acquéreur TOKEN (+ crypto) TOKEN marchand / PSP (souvent)
Risque type Device perdu · clone NFC Compte app compromis Fuite base COF · MIT abusif

Ancrage

Question salle

Où reste le PAN — et quel domaine ?

  • Vault / TSP / issuer — pas chez le marchand ni au POS
  • Token in-store (device) ≠ token COF e-commerce
  • Même rail J1 — contexte d’émission différent

3.2 · Tokenisation réseau & cycle de vie

Tokenisation réseau & cycle de vie

Définition monétique

Qu’est-ce que le lifecycle du token ?

Ensemble des états et transitions d’un token : provisioning → actif (usage Auth) → suspendre / reprendre → supprimer. Distinct du cycle de la carte source : on gouverne un device / canal sans résilier le PAN. Durée = états, pas un TTL type OTP.

Parcours

Une seule carte du cycle

Quatre temps — détaillés ensuite : provisioning, stockage, Auth, gouvernance.

Provision · Actif · Suspendre · Supprimer

États gouvernés par le TSP · ≠ cycle carte

Longue durée tant qu’actif · crypto de chaque txn = éphémère · détail des actions = section Gouvernance plus bas.

Provisioning

Enrôlement & provisioning

Demande d’usage → contrôles → création du token et rattachement au device / canal.

Enrôlement

Porteur · wallet · TSP · issuer

Après provisioning

Où est stocké le token

Deux niveaux : vault (lien) vs credential (là où on paie). Vocabulaire vault / TSP : Définition ; terrains : Domaines.

Stockage dual

Contraste lien / présentation — pas un 2e cours domaines

Usage · Auth

Qui voit le token · qui voit le PAN

En network tokenization, c’est le token qui part en autorisation jusqu’à l’acquéreur — le PAN n’apparaît qu’au moment de la détokenisation (réseau / TSP), pour joindre l’issuer.

Chaîne Auth tokenisée

Token chez l’acquéreur · PAN seulement après détokenisation

Nuance à dire en salle

Network token ≠ token vault marchand seul

Routage détaillé (qui acquiert · qui AuthZ) : 3.3 · Architecture SI.

Gouvernance

Activer · Suspendre · Supprimer

Détail des états de la carte du cycle — actions fines sur un contexte, sans forcément toucher toute la carte.

Actions TSP

Device perdu · fraude · fin d’usage

Intro crypto

Cryptogrammes dynamiques

Le token protège l’identifiant ; le cryptogramme protège l’usage dans le temps et le contexte.

Token + cryptogramme

Données dynamiques · anti-réutilisation

Intro seulement — détail SE / HCE / TEE en Jour 4.

Ancrage

Cas pratiques

Cas 1 — Device perdu

  • Suspendre le token
  • Carte source intacte

Cas 2 — Nouveau device

  • Nouveau provisioning
  • Même PAN, nouveau contexte

Cas 3 — Chez l’acquéreur ?

  • Network token → TOKEN en Auth
  • Vault marchand seul → PAN possible

Cas 4 — Carte réémise

  • Re-liaison / re-provision
  • COF : mapping TSP peut survivre

Clarification

Ce que ce n’est pas

Lifecycle token ≠ cycle carte

On peut suspendre un device sans résilier la carte.

Token ≠ cryptogramme

Durable vs preuve dynamique (éphémère) d’une txn.

Vault ≠ credential d’usage

Le vault détient le lien ; le device / marchand présente.

Acquéreur ≠ détenteur du PAN

En network tokenization, l’acquéreur voit le token ; le PAN apparaît à la détokenisation réseau / TSP.

≠ Cours SE / HCE

Secure Element, HCE, TEE = Jour 4.

3.3 · Architecture SI

Architecture SI tokenisation

Définition

Que montre l’architecture SI ?

Les briques qui émettent, stockent et présentent le token — puis qui acquiert le flux Auth et route jusqu’à l’AuthZ émetteur. Cycle de vie (états) : 3.2.

Éléments SI

Où tournent les briques

Briques tokenisation

App / wallet · Acceptation · PSP · TSP · Scheme · SI issuer

Routage Auth

Qui acquiert · comment ça route

Network tokenization : jusqu’à l’acquéreur inclus = TOKEN (+ crypto). Détokenisation au TSP / scheme → AuthZ SI issuer.

Flux Auth tokenisé

Présentation → PSP → TSP → scheme → SI AuthZ

Vault marchand / PSP seul : le PSP peut détokeniser avant l’acquéreur — celui-ci peut alors revoir du PAN. Détail domaines : 3.1.

Synthèse

Qui voit quoi · qui AuthZ

Acteur Voit Rôle
App / wallet TOKEN (+ crypto) Présente le credential
Acceptation · PSP / acquéreur TOKEN (network tok.) Acquiert le flux Auth
TSP Mapping TOKEN ↔ PAN Gouverne · détokenise
Scheme Rail / routage Route vers l’émetteur
SI issuer Compte / PAN + règles token AuthZ OK / KO

TSP ≠ issuer : gouvernance du token d’un côté ; produit carte et décision AuthZ de l’autre. Network tokenization (VTS / MDES…) = service scheme / TSP.

Clarification

Ce que ce n’est pas

Token ≠ remplacement de l’émetteur

Substitut d’identifiant — pas la décision de paiement.

≠ Architecture wallet complète

SE / HCE / TEE et détail NFC = Jour 4.

3.4 · Sécurité & conformité

Sécurité & conformité

Définition monétique

Que couvre ce bloc ?

Les mécanismes qui accompagnent la tokenisation : device binding, SCA / DSP2, cryptogrammes, impact PCI-DSS et protection des données. La tokenisation réduit l’exposition du PAN ; elle ne remplace ni authentification forte, ni gouvernance, ni audit.

Sécurité de l’identifiant ≠ sécurité de l’authentification.

Vocabulaire

Socle sécurité réutilisable

Trois leviers complémentaires — à ne pas fusionner.

Device binding · SCA · Cryptogrammes

Identifiant · identité · usage transactionnel

Conformité

PCI-DSS & protection des données

La tokenisation aide à réduire le scope — elle ne ferme pas le dossier conformité.

Exposition · Scope · Gouvernance

Ce que la tokenisation change — et ce qu’elle ne change pas

Avant tokenisation Après tokenisation
Chez le marchand PAN stocké / transmis → scope PCI large TOKEN (souvent) → scope potentiellement réduit
Ce qui reste Vault / TSP, audit, gouvernance, SCA, responsabilités issuer
Piège « Tokenisé ⇒ conforme » — faux ; réduction à valider, pas à proclamer

PCI-DSS

  • Réduction d’exposition du PAN
  • Allègement possible de périmètres
  • Gouvernance ne disparaît pas

Protection des données

  • SCA reste un sujet distinct
  • Traçabilité et conservation
  • Responsabilités TSP / issuer / wallet

Rôle

Ce qu’on réduit, ce qu’on garde

Réduit

Exposition du PAN, réutilisation triviale, certains risques côté marchand.

Conservé

Fraude, gouvernance des tokens, compromission de device, erreurs d’intégration, exigences d’audit.

Déplacé

Une part de responsabilité se concentre sur TSP, issuer, wallet et briques de confiance.

Pont J4

Pourquoi ce bloc précède wallets et NFC

Apple Pay, Google Pay, SE, HCE et TEE seront lisibles si l’on a déjà dissocié carte source, token, cryptogramme et device.

J3 → J4

Tokenisation · crypto · device → wallets / NFC
