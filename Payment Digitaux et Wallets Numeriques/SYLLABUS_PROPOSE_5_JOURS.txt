PRE-SYLLABUS PROPOSE — Paiements digitaux & Wallets numériques
M2 SIB — 5 jours × 4h (20h)
Organisation revue : tokenisation avant NFC / wallets
Public cible : professionnels de la banque (dimension palpable recommandée en fin de chaque jour)


Objectifs généraux (inchangés)
À l’issue du cours, les étudiants seront capables de :
- Comprendre les architectures des systèmes de paiement digitaux
- Analyser les technologies QR Code, NFC et tokenisation
- Expliquer le fonctionnement des wallets numériques
- Modéliser les flux transactionnels carte et wallet
- Comprendre les standards internationaux (EMV, ISO)
- Concevoir une architecture SI de paiement omnicanale
- Identifier les enjeux de sécurité, conformité et gouvernance


================================================================================
JOUR 1 — Écosystème & flux carte (4h)
================================================================================
Objectif du jour : poser le socle métier et transactionnel avant les canaux digitaux.

1.1 Évolution des systèmes de paiement
- Paiement cash → carte → mobile → wallet
- Paiements électroniques vs paiements digitaux
- Paiements en ligne, de proximité et in-app
- Paiements temps réel vs différés

1.2 Écosystème des paiements digitaux
Acteurs clés :
- Banques émettrices & acquéreuses
- Réseaux cartes (Visa, Mastercard)
- Schemes de paiement
- Fintechs & PSP
- Constructeurs de devices
- Wallet providers (mention acteur uniquement, sans détail interne)

Introduction aux standards internationaux (EMV / ISO)
→ bloc dédié J1 (après Acteurs, avant Chaîne de valeur)
  · EMVCo : Chip · 3DS · QR · Token
  · ISO : 8583 · 14443 · 20022
  · Wallet = empilement (14443 + EMV CL + tokenisation), pas un ISO unique

1.3 Architecture générale d’un système de paiement
Chaîne de valeur :
- Client → terminal → acquéreur → réseau → émetteur

Composants SI (vue métier, pas plateforme complète) :
- POS / terminal mobile
- Payment gateway
- Acquiring system
- Issuing system
- Clearing & settlement

1.4 Flux transactionnel carte
Analyse détaillée :
- Autorisation
- Authentification
- Clearing
- Settlement

Notions :
- Online vs offline transaction
- Latence & disponibilité
- Gestion des rejets
- Rappel : le PAN circule dans le modèle carte classique (pont vers J3 tokenisation)

--- Proposition élément palpable (physique / logiciel) ---
- Physique : terminal Ingenico Lane 5000 (param TEST) + cartes de test contact / sans contact
- Logiciel : Postman + collection mock auth approve / decline ; sandbox PSP optionnelle
- Atelier suggéré (~75–90 min) :
  · Rail A — init terminal → transactions contact/CL → lecture ticket → télécollecte
  · Rail B — Postman approve / decline → placement champs sur la chaîne
  · Optionnel : annulation, remboursement, seuil CL, échec réseau
- Règle : cartes / MID / TID / clés de test uniquement — jamais de production


================================================================================
JOUR 2 — Paiements par QR Code (4h)
================================================================================
Objectif du jour : maîtriser un canal digital « software-first », sans prérequis token/SE.

2.1 QR Code : principes et typologies
- QR statique vs QR dynamique
- QR push vs QR pull
- QR closed-loop vs open-loop
- QR bancaire vs QR wallet (wallet = canal côté UX ; détail technique reporté J4)

2.2 Architecture SI du paiement QR
Composants :
- Application client
- QR engine
- Backend marchand
- PSP / switch
- Banque ou wallet

Modélisation des flux :
- génération du QR
- scan & validation
- autorisation
- confirmation

2.3 Standards QR et interopérabilité
- EMV QR Code
- QR national vs QR international
- Interopérabilité multi-wallet
Cas d’usage :
- commerce de proximité
- transport
- paiements P2P

2.4 Cas pratique (allégré)
Étude de cas : conception d’un système de paiement QR national interopérable
Livrables étudiants :
- schéma d’architecture
- flux transactionnels
- acteurs & responsabilités
Note : la plateforme omnicanale complète (QR + NFC + wallet) est réservée au J5.

--- Proposition élément palpable (physique / logiciel) ---
- Physique : stickers / présentoir QR « marchand » ; 1 téléphone caisse + 1 téléphone client
- Logiciel : générateur QR statique vs dynamique ; optionnel parseur payload type EMV QR
- Atelier suggéré (~60 min) : groupe marchand génère les 2 QR, groupe client scanne, comparer le payload, tracer le flux jusqu’à confirmation
- Débat terrain : closed-loop vs open-loop, push vs pull — avec l’objet en main


================================================================================
JOUR 3 — Tokenisation & sécurité des paiements (4h)
================================================================================
Objectif du jour : poser le modèle de sécurité réutilisé par NFC et wallets.

3.1 Tokenisation des paiements
Définition :
- PAN vs Token
- Token vault
- Token service provider (TSP)

Domaines d’usage :
- in-store
- in-app
- e-commerce

Objectifs :
- réduction de la fraude
- conformité PCI-DSS
- limitation de l’exposition du PAN

3.2 Network tokenization & lifecycle
- Enrolment / provisioning (vue conceptuelle)
- Utilisation du token en transaction
- Lifecycle du token (activation, suspension, suppression)
- Cryptogrammes dynamiques (introduction)

3.3 Architecture SI liée à la tokenisation
Composants :
- merchant / wallet
- TSP
- network tokenization
- bank issuer system

Flux simplifié :
- demande de token
- stockage sécurisé
- présentation du token à l’autorisation

3.4 Sécurité et conformité (socle)
Mécanismes :
- device binding
- authentification forte (lien DSP2 / SCA)
- cryptogrammes

Réglementation :
- PCI-DSS
- DSP2 / SCA
- protection des données

Lien pédagogique explicite : ce modèle sera appliqué au paiement NFC mobile (J4).

--- Proposition élément palpable (physique / logiciel) ---
- Physique / visuel (à apporter) : carte plastique + captures wallet (Apple Pay / Google Pay) — PAN masqué vs token / DAN ; visuels support (Définition)
- Logiciel : simulateur maison PAN ↔ token ↔ lifecycle (provision → pay → suspend → delete) — pas VTS/MDES sauf accès banque existant
- Atelier suggéré (~60 min) : partir du message d’auth J1, scénario tokenisé, jouer le lifecycle, relier au scope PCI
- Achat matériel : aucun — prep simulateur + visuels


================================================================================
JOUR 4 — NFC, sans contact & wallets numériques (4h)
================================================================================
Objectif du jour : appliquer tokenisation + environnements sécurisés au canal de proximité et aux wallets.

4.1 Technologie NFC
- Principes physiques
Modes NFC :
- Card emulation
- Reader / writer
- Peer-to-peer
- NFC vs QR : avantages et limites

4.2 Paiement sans contact EMV
Fonctionnement :
- carte sans contact (plastique)
- mobile NFC
- seuils de paiement
- offline transactions

Standards :
- EMV Contactless
- ISO 14443

4.3 Architecture NFC mobile & wallets
Composants de confiance :
- Secure Element (SE)
- Host Card Emulation (HCE)
- TEE (Trusted Execution Environment)

Comparaison :
- SIM-based SE
- Embedded SE
- Cloud-based HCE

Wallets majeurs (sections dédiées) :
- Apple Pay (SE · Enclave · CDCVM · flux)
- Google Pay (HCE / TEE · CDCVM · flux · vs Apple)

Fonctions wallet :
- stockage des tokens
- authentification biométrique
- orchestration du paiement

Architecture SI d’un wallet :
- wallet app
- TSP / network tokenization
- bank issuer system

Flux :
- enrolment carte
- provisioning
- paiement
- lifecycle du token (mise en pratique J3)

4.4 Cas pratique (1h)
Analyse d’un paiement NFC : smartphone → POS
Les étudiants identifient :
- composants impliqués (SE/HCE, token, TSP, POS, acquéreur, émetteur)
- messages échangés
- points de sécurité critiques
Prérequis mobilisés : J1 (flux carte) + J3 (tokenisation) + J4 (NFC/wallet)

--- Proposition élément palpable (physique / logiciel) ---
- À acheter / apporter : module PN532 (antenne visible), lecteur USB NFC type ACR122U, tags NFC (NTAG), carte sans contact, smartphones Apple Pay / Google Pay
- Logiciel : app NFC Tools ; optionnel démo HCE Android (non bancaire)
- Atelier suggéré (~75 min) : montrer l’antenne → lire tag/carte (UID, ISO 14443) → tester la distance → relier au paiement smartphone→POS (SE / HCE / token J3)
- Attention : lecture UID / présence puce uniquement, pas d’extraction de données sensibles

JOUR 5 — Paiements omnicanaux & conception SI (4h)
================================================================================
Objectif du jour : synthétiser QR + token + NFC/wallet dans une plateforme SI.

5.1 Paiement omnicanal
Cas :
- in-store
- e-commerce
- mobile
- in-app

Concepts :
- single payment backend
- orchestration multi-moyens
- expérience utilisateur unifiée

5.2 Architecture d’une plateforme de paiement digitale
Composants :
- payment gateway
- wallet manager
- tokenization service
- fraud engine
- reconciliation & settlement

Exigences transverses :
- architecture scalable & sécurisée
- interopérabilité
- gouvernance

5.3 Contrôle continu
Concevoir une plateforme de paiement digital nationale
Exigences :
- QR + NFC + wallet
- interopérabilité
- sécurité
- gouvernance

Livrables :
- schéma d’architecture
- flux détaillés
- justification des choix techniques

--- Proposition élément palpable (physique / logiciel) ---
- Logiciel : réutiliser collection Postman J1 — mock gateway 3 moyens (carte, QR, token wallet) + journal unique
- Physique (salle / consommable) : mur d’architecture post-its ou aimants (gateway, TSP, fraud, settlement…)
- Atelier / contrôle (~2h) : brancher 3 canaux sur mock, 1 paiement par canal, livrer schéma + flux + justification, pitch comité SI
- Achat matériel : aucun matériel métier — post-its / tableau = consommable salle

Logique pédagogique (rappel)
================================================================================

Écarts vs pré-syllabus initial

- Wallets regroupés avec NFC (J4), plus seulement évoqués en acteurs (J1)
- Architecture SI « plateforme » concentrée en J5 (J1 reste chaîne de valeur / flux carte)
- Cas QR J2 allégé ; cas intégrateur national en J5
- En fin de chaque jour : proposition d’élément physique ou logiciel pour ancrer le cours (public banque)
