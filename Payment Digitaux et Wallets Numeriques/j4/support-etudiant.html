4.1 · Technologie NFC / sans contact

Technologie NFC / sans contact

Définition

Qu’est-ce que le NFC ?

NFC (Near Field Communication) : communication radio à très courte distance (centimètres), bidirectionnelle, pensée pour des interactions de proximité (« tap »). En paiement, c’est le canal physique entre le support (carte / mobile) et le terminal — distinct du QR (canal optique) et distinct de la tokenisation (identifiant présenté).

Principes physiques

Caractéristiques physiques essentielles

Distance courte, induction, antenne — le geste « tap » n’est pas cosmétique.

Proximité radio

13,56 MHz · induction · distance · empilement de couches

Couche Contenu Rôle
Physique RF 13,56 MHz · induction · ~cm Le « tap » fonctionne (ou pas)
ISO/IEC 14443 Proximité Type A/B · APDU Protocole carte ↔ lecteur
NFC Device · card emulation… Le téléphone joue une carte
EMV Contactless Risque · CVM · crypto Payer en sécurité → 4.2

Actif / passif

« Passif » = rôle RF face au champ, pas « sans batterie ». En wallet, le téléphone a de l’énergie, mais le POS reste l’Initiator.

ISO/IEC 14443

Type A / Type B

Temps 1

Une norme, deux déclinaisons

ISO/IEC 14443 = la norme du sans contact de proximité (13,56 MHz, carte ↔ lecteur). Elle se décline en deux types : A et B.

Temps 1 · La norme se divise

14443 → Type A · Type B

Temps 2

Ce qui différencie A et B

Différence radio seulement — pas Visa vs Mastercard.

Le lecteur module le champ 13,56 MHz : A = fort, B = léger.

ASK (Amplitude Shift Keying) : modulation par variation d’amplitude du champ radio.

Temps 2 · Comment le signal est modulé

Lecteur → carte · même fréquence, deux enveloppes

Type A Type B
Modulation lecteur → carte ASK 100 % (forte) ASK 10 % (légère)
Compatible ? Non — A ne parle pas à B
Terrain Majoritaire · NFC-A Minoritaire · NFC-B
Au-dessus Identique · APDU · EMV Contactless
Com radio Type A Type B
Avantages Contraste d’amplitude maximal (ASK 100 %) · bits plus faciles à départager · détection / décodage côté carte et lecteur souvent plus simple Champ continu (ASK 10 %) · alimentation RF de la carte non coupée pendant la modulation · liaison plus « douce » pour démarrer et tenir la session
Inconvénients Coupures de champ (quasi OFF) · la carte doit tenir sans énergie RF sur ces instants · modulation plus brutale à l’établissement du dialogue Variation d’amplitude faible · contraste plus difficile à lire · exige un récepteur plus sensible pour établir et suivre le signal
En résumé A = radio « tranchée » (lisible, mais coupures) · B = radio « continue » (stable en énergie, mais signal plus fin) — ni A ni B interopérables entre eux
  • Carte / wallet paiement : Type A quasi exclusif.
  • POS certifié contactless : A et B (interop 14443) — filet pour les cartes B rares, pas le chemin courant.
  • Match : carte A ↔ POS A · carte B ↔ POS B.

Empilement

Où se placent A et B dans les couches

Type A / Type B = choix en bas (radio). Au-dessus, APDU et EMV sont les mêmes — quel que soit le type.

Couches · du bas (RF) vers le haut (paiement)

ISO 14443 = couche radio · A / B = fourche dedans

Choix marché

Pourquoi le paiement a choisi Type A

Type A · chemin dominant du paiement

Masse critique → standard de fait

Pour le tap carte / wallet au POS, on raisonne Type A. Le POS gère aussi B pour l’interop 14443 (carte B rare), pas parce que B est le chemin principal du paiement.

Interop radio

Quand l’un est A et l’autre B

A et B ne se comprennent pas au niveau radio. Il faut le même type des deux côtés (carte / wallet ↔ POS), sinon le tap échoue avant même l’EMV.

Carte / wallet × POS · même type ou échec

Quatre cas · une seule règle

Modes NFC

Trois modes à connaître

Un chipset, trois usages — seul le mode card emulation porte le paiement wallet.

Card emulation · Reader/writer · P2P

Rôles du device NFC

Reader / writer

Face au POS, le déroulement est le même qu’une carte sans contact (champ → Type A → APDU EMV CL → AuthZ). Ce qui change = le card emulation : le téléphone joue le rôle de la carte (SE / HCE + token), le POS ne voit pas un « app ».

Normes

NFC Forum vs ISO 14443

Deux acteurs différents : ISO/IEC 14443 = tuyau radio carte ↔ lecteur · NFC Forum = comment un device NFC (téléphone, tag…) utilise ce tuyau et interopère. Le Forum n’est pas la spec monétique.

Ce que fait le NFC Forum

Consortium · specs device / tags / données — sur socle ISO

Ce que le NFC Forum spécifie

  • Modes · Digital Protocol (NFC-A/B/F/V) · Activity / Profiles
  • Tags · NDEF / RTD · LLCP / SNEP (P2P)
  • Device Requirements · Analog · Connection Handover

Ce que le NFC Forum ne fait pas

  • Pas de logique paiement : pas de CVM, seuils, cryptogrammes EMV, AuthZ, tokenisation.
  • Ça, c’est EMVCo (EMV Contactless) + schemes + TSP (J3) — pas le Forum.

Card emulation : le téléphone « ressemble » à une carte face à un POS déjà calé sur 14443 + EMV — le terminal n’a pas besoin de connaître tout le catalogue Forum pour accepter le tap.

4.2 · Paiement sans contact EMV

Paiement sans contact EMV

Définition

Qu’est-ce que le sans contact EMV ?

Paiement carte (ou équivalent mobile) via interface de proximité (ISO 14443), sous le cadre EMV Contactless : mêmes familles de contrôles (authentification données, CVM, risque, online/offline), avec un geste « tap » et des seuils / paramètres spécifiques au canal.

Canal physique : 4.1 NFC / sans contact · identifiant tokenisé : J3.

Contact · sans contact

7816 vs 14443 — même logique EMV

Le sans contact change le tuyau, pas la philosophie monétique. Les APDU restent structurées par ISO/IEC 7816-4.

Canal Interface Transport Logique paiement
Contact ISO/IEC 7816 (contacts) Fils · puce insérée EMV (Contact / Contactless)
Sans contact ISO/IEC 14443 (RF 13,56 MHz) APDU 7816-4 sur le canal RF

4.3 · Wallets & confiance device

Architecture NFC mobile & wallets

Définition monétique

Qu’est-ce qu’un wallet de paiement ?

App + couches du téléphone (NFC, SE/HCE, TEE…) qui enrolent un token, authentifient le porteur, et le présentent au POS comme une carte — sans décider l’AuthZ (rôle émetteur).

Avant SE / HCE : ce que la puce carte classique porte déjà — même famille de secrets, autre boîte.

Référence · carte plastique

Que contient une puce classique ?

Sur une carte EMV (contact ou sans contact), la puce ICC héberge une application de paiement : c’est dans cette appli que vivent le PAN, les secrets longs et les compteurs. Le wallet mobile ne « invente » pas ces objets : il les reloge (SE) ou les compense (HCE + TSP).

Puce ICC · ce qu’elle porte pour payer

Appli EMV ⊃ PAN · UDK-AC · ATC — vocabulaire repris plus bas

Confiance device

SE · HCE

Deux modèles pour répondre au POS en card emulation : puce coffre (SE) ou logiciel + TSP (HCE).

1 · SE

Secure Element

Une puce dédiée qui est la carte sans contact face au POS — même logique que l’ICC plastique.

  • Une appli avec identifiant (souvent token / DPAN)
  • La UDK-AC : clé unique dérivée de la clé maître émetteur (IMK-AC) — secret long / durable pour le cryptogramme
  • Isolée de l’OS : ce n’est pas l’app wallet qui « joue » la carte

SE · où · quoi pour le tap

Même boîte que l’ICC · UDK-AC reste dans la puce

2 · HCE

HCE · ce qui manque vs SE → nécessité du TSP

Host Card Emulation : le logiciel (OS / app) émule une carte sans contact face au POS.

  • Pas de coffre matériel : en général pas d’UDK-AC sur le téléphone (secret long / durable dérivé de la clé maître émetteur)
  • Le TSP garde l’UDK-AC chez lui
  • Il n’envoie au téléphone que des credentials à durée / usage limités (clés ou jetons courts) pour les taps

HCE sur le phone · lien TSP

UDK-AC au TSP · credentials courts rechargés sur le HCE

« Court » = durée de vie limitée (HCE)
Secret long UDK-AC reste au TSP — jamais en stock durable sur le phone
Credentials / LUK
Limited Use Key 		Clé à usage limité · vie courte (TTL heures/jours et/ou nb de taps) — pas « clé plus petite »
Quand envoyés ? (1) à l’enrolment · (2) recharge amont quand le phone est online (Wi‑Fi / data)
Pas au tap Le POS parle au HCE, pas au TSP — pas de recharge via le terminal
Offline Utilise un credential encore valide · stock épuisé → tap bloqué jusqu’à la prochaine recharge

À ce stade

SE = la carte (puce + secrets) · HCE = logiciel sur le téléphone qui joue la carte (+ TSP pour le secret durable). Ensuite : où vit le coffre (SIM · eSE · cloud / TSP).

Implémentations

SIM · eSE · HCE cloud

Pas un 3ᵉ modèle à côté de SE / HCE : ici on regarde où vit le coffre (secret durable) et qui le gouverne.

  • SE · HCE = comment on répond au POS
  • Même modèle SE, deux boîtes : SE dans la SIM ((Subscriber Identity Module) ou SE dans l’eSE ((embedded Secure Element)
  • HCE cloud (Cloud-based HCE) = HCE sur le téléphone + coffre chez le TSP — pas « HCE dans le cloud »

Une grille · trois questions

Coffre · gouvernance · qui répond au POS (HCE = toujours sur le phone)

Lire la grille

Colonnes 1 et 2 = même modèle SE (applet + token + UDK-AC locale), boîte différente. Colonne 3 = modèle HCE déjà vu : le stack qui parle au POS est sur le téléphone ; « cloud » = uniquement où vit le secret durable (TSP).

Confiance device · suite

TEE

On sait déjà :

  • qui répond au POS — SE ou HCE
  • où c’est logé — SIM · eSE · cloud

Le TEE n’est pas un 3ᵉ modèle de card emulation : c’est la couche qui autorise le porteur (CDCVM) et protège l’usage.

Définition

TEE · autorise le porteur · ≠ carte · ≠ SE

Trusted Execution Environment : zone isolée dans le processeur (SoC), séparée du rich OS. Elle n’est pas la carte sans contact et n’est pas la puce SE — elle autorise / protège (biométrie, CDCVM) pour que SE ou HCE puisse parler au POS.

TEE · où · ce qu’il fait · ce qu’il n’est pas

Partition CPU · preuve porteur · pas le canal RF

Assemblages terrain

Couples · SE + TEE · HCE + TEE

Le TEE s’ajoute à SE ou à HCE pour le CDCVM (Consumer Device Cardholder Verification Method : vérification du porteur sur le device — biométrie / code) et la protection : il ne remplace ni l’un ni l’autre.

Deux couples produits

Qui joue la carte · qui autorise le porteur

Ne pas confondre

SE = la carte (puce + secrets) · HCE = logiciel qui joue la carte · TEE = isolation CPU pour CDCVM (Consumer Device Cardholder Verification Method) — pas le canal RF. Un device combine souvent SE + TEE ou HCE + TEE.

Produits

Wallets · combinaisons

Un wallet assemble les briques déjà vues : coffre (où) · qui répond au POS · TEE pour le CDCVM.

Apple Pay · Google Pay

Même geste tap · deux stacks

Détail flux : Apple Pay · Google Pay.

Synthèse

Exemple A · Apple Pay

Comment ajouter une carte

Sur iPhone : Wallet orchestre · le TSP crée le token · l’émetteur autorise · le secret durable va dans l’eSE.

Étape Sur le téléphone Côté réseau
1 Ouvrir l’app Wallet (icône préinstallée iPhone) → + en haut à droite → Carte de débit ou de crédit —
2 Continuer → scan caméra ou Saisir les détails de la carte → Suivant · accepter les conditions Wallet → demande d’enrolment au TSP
3 Choisir la vérif. (SMS, appel, app banque) · saisir le code Émetteur valide le porteur (IDV)
4 Carte apparaît dans Wallet · Face ID / Touch ID prêts TSP provisionne le token dans l’eSE (UDK-AC locale)

Repère : tant que l’étape 3 n’est pas validée, aucun token n’est utilisable au POS.

Exemple B · Google Pay / Google Wallet

Comment ajouter une carte (Android)

Sur Android, l’app s’appelle Google Wallet (pas un dossier « Wallet » générique). Google Pay = le paiement ; Google Wallet = l’app où on ajoute la carte. Si absente : Play Store → « Google Wallet ».

Étape Geste exact sur Android Côté réseau
0 Tiroir d’apps → rechercher Wallet ou Google Wallet · sinon installer depuis le Play Store · se connecter au compte Google —
1 Ouvrir Google Wallet → en bas Ajouter à Wallet —
2 Carte de paiement → Nouvelle carte de crédit ou de débit → scan caméra ou saisie manuelle → Enregistrer et continuer Demande d’enrolment au TSP
3 Lire / Accepter les CGU émetteur · choisir la vérif. (SMS, e-mail, app banque) · saisir le code Émetteur valide le porteur (IDV)
4 Carte visible dans Google Wallet · activer NFC · Réglages → Appareils connectés → Préférences de connexion → Paiements sans contact → choisir Google Wallet (défaut) Token prêt · UDK-AC au TSP · HCE + LUK (credentials courts)

Repère : sans app Google Wallet + NFC défaut, le tap POS échoue même si la carte est « dans Google ». Secret long au TSP · LUK rechargés online.
