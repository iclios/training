4.3 · Wallet majeur

Apple Pay

Définition

Qu’est-ce qu’Apple Pay ?

Wallet Apple qui orchestre enrolment, token réseau, CDCVM et présentation du credential — sans remplacer l’émetteur ni l’AuthZ.

Point Apple Pay
Stack eSE + Secure Enclave (déjà vu Architecture wallets)
Trois canaux proximité (NFC) · in-app · e-commerce
TSP (VTS / MDES…) = vault token · détokenisation Auth — pas Apple

J3 lifecycle · Google Pay

Plateforme

Écosystème Apple

Un parc maîtrisé (matériel + OS) — moins de fragmentation qu’Android, exigences device plus uniformes pour l’émetteur.

OS · form factors · NFC

Vue d’ensemble — tout visible

1 · OS

iOS · watchOS · PassKit

PassKit = API wallet — UX enrolment, liste des cartes, initiation du paiement.

Parc homogène : versions OS et capacités NFC plus prévisibles pour un issuer.

Cible device « Apple » plus standardisée qu’Android multi-OEM.

2 · Devices

iPhone · Watch · domaines token

iPhone : token device-bound pour le tap de proximité.

Apple Watch : souvent un autre token / domaine (montre ≠ téléphone).

Perte d’un device → revoke ciblé — rappel J3 Domaines.

3 · NFC

Card emulation

Le device se comporte comme une carte sans contact face au TPE (ISO 14443 / EMV Contactless).

Sortie = token + cryptogramme — pas le PAN d’origine (J3 Auth).

Prérequis : POS contactless + acceptation wallet.

Écosystème

Tous les acteurs monétiques

Apple Pay s’insère dans la chaîne J1 — chaque maillon a un rôle précis — vue d’ensemble.

Chaîne complète Apple Pay

Porteur → Wallet → TSP → Issuer · POS → Acquéreur → Auth

Porteur

CDCVM · geste

Ajoute la carte, valide l’IDV / OTP, authentifie chaque paiement (Face ID / Touch ID / code).

Déclenche l’enrolment — ne crée pas le token.

Apple Wallet

PassKit · SE · orchestre

UX, SE, demande d’enrolment au TSP, présentation NFC. ≠ banque · ≠ TSP · ≠ AuthZ.

Au tap NFC : token dans le SE — pas le PAN.

TSP / scheme

VTS · MDES · vault

Émet le token, domaine device, vault PAN↔token, états actif / suspend / delete. En Auth : détokenise.

≠ CB2A · ≠ Apple Wallet.

Issuer

PAN · AuthZ · décide

Compte / PAN · OK provisioning · AuthZ OK/KO. Racine monétique inchangée.

Opposition carte ≠ automatiquement tous les tokens.

POS

NFC EMV · voit TOKEN

TPE contactless · reçoit le tap · Auth comme carte sans contact. DPAN + crypto — pas le PAN d’origine.

Le POS n’est pas le TSP.

Acquéreur / PSP

Auth TOKEN

Routage Auth en network tokenization — reçoit le TOKEN. Clearing / settlement = rail J1.

Au tap NFC : TOKEN jusqu’à l’acquéreur.

Provisioning ↑ · Paiement NFC → POS · acquéreur · réseau détokenise · issuer

Confiance device

Workflow · ajouter une carte

Même composants : demande au TSP · Issuer répond au TSP · TSP provisionne le téléphone (PassKit → eSE).

Use case : ajouter sa CB dans Wallet pour pouvoir payer ensuite (tap, in-app, web).

Canal 1 · Proximité

Workflow Apple Pay · tap

Tous les composants déjà vus, enchaînés : CDCVM → eSE ↔ POS (APDU) → Auth tokenisée via TSP.

Use case : payer au TPE (boulangerie, métro, caisse magasin) — iPhone près du lecteur.

Canal 2 · In-app

Workflow Apple Pay · in-app

Pas de RF : session PassKit dans l’app · CDCVM → payload TOKEN → Auth via TSP (même famille Auth · domaine souvent distinct du NFC, J3).

Use case : payer un trajet Uber / une commande Deliveroo dans l’app — bouton Apple Pay.

Architecture fléchée · app → PSP → Auth

Req ↓ · Rsp ↑ · numéros = ordre · ≠ APDU POS

Canal 3 · E-commerce

Workflow Apple Pay · e-commerce

Site ouvert dans Safari iOS : le bouton Apple Pay n’appelle pas un wallet distant — Safari déclenche la feuille Apple Pay native du téléphone (même PassKit / Enclave / token que l’in-app) · CDCVM → TOKEN → Auth via TSP.

Use case : checkout web sur le téléphone (Zara, Fnac… dans Safari iOS). Sur PC, pas d’accès direct au wallet iPhone — d’où le focus mobile ici.
