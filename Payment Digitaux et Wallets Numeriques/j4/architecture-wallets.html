4.3 · Wallets & confiance device

Architecture NFC mobile & wallets

Définition monétique

Qu’est-ce qu’un wallet de paiement ?

App + couches du téléphone (NFC, SE/HCE, TEE…) qui enrolent un token, authentifient le porteur, et le présentent au POS comme une carte — sans décider l’AuthZ (rôle émetteur).

Avant SE / HCE : ce que la puce carte classique porte déjà — même famille de secrets, autre boîte.

Référence · carte plastique

Que contient une puce classique ?

Sur une carte EMV (contact ou sans contact), la puce ICC héberge une application de paiement : c’est dans cette appli que vivent le PAN, les secrets longs et les compteurs. Le wallet mobile ne « invente » pas ces objets : il les reloge (SE) ou les compense (HCE + TSP).

Confiance device

SE · HCE

Deux modèles pour répondre au POS en card emulation : puce coffre (SE) ou logiciel + TSP (HCE).

1 · SE

Secure Element

Une puce dédiée qui est la carte sans contact face au POS — même logique que l’ICC plastique.

  • Une appli avec identifiant (souvent token / DPAN)
  • La UDK-AC : clé unique dérivée de la clé maître émetteur (IMK-AC) — secret long / durable pour le cryptogramme
  • Isolée de l’OS : ce n’est pas l’app wallet qui « joue » la carte

SE · où · quoi pour le tap

Même boîte que l’ICC · UDK-AC reste dans la puce

2 · HCE

HCE · ce qui manque vs SE → nécessité du TSP

Host Card Emulation : le logiciel (OS / app) émule une carte sans contact face au POS.

  • Pas de coffre matériel : en général pas d’UDK-AC sur le téléphone (secret long / durable dérivé de la clé maître émetteur)
  • Le TSP garde l’UDK-AC chez lui
  • Il n’envoie au téléphone que des credentials à durée / usage limités (clés ou jetons courts) pour les taps

HCE sur le phone · lien TSP

UDK-AC au TSP · credentials courts rechargés sur le HCE

À ce stade

SE = la carte (puce + secrets) · HCE = logiciel sur le téléphone qui joue la carte (+ TSP pour le secret durable). Ensuite : où vit le coffre (SIM · eSE · cloud / TSP).

Implémentations

SIM · eSE · HCE cloud

Pas un 3ᵉ modèle à côté de SE / HCE : ici on regarde où vit le coffre (secret durable) et qui le gouverne.

  • SE · HCE = comment on répond au POS
  • Même modèle SE, deux boîtes : SE dans la SIM ((Subscriber Identity Module) ou SE dans l’eSE ((embedded Secure Element)
  • HCE cloud (Cloud-based HCE) = HCE sur le téléphone + coffre chez le TSP — pas « HCE dans le cloud »

Confiance device · suite

TEE

On sait déjà :

  • qui répond au POS — SE ou HCE
  • où c’est logé — SIM · eSE · cloud

Le TEE n’est pas un 3ᵉ modèle de card emulation : c’est la couche qui autorise le porteur (CDCVM) et protège l’usage.

Définition

TEE · autorise le porteur · ≠ carte · ≠ SE

Trusted Execution Environment : zone isolée dans le processeur (SoC), séparée du rich OS. Elle n’est pas la carte sans contact et n’est pas la puce SE — elle autorise / protège (biométrie, CDCVM) pour que SE ou HCE puisse parler au POS.

TEE · où · ce qu’il fait · ce qu’il n’est pas

Partition CPU · preuve porteur · pas le canal RF

Assemblages terrain

Couples · SE + TEE · HCE + TEE

Le TEE s’ajoute à SE ou à HCE pour le CDCVM (Consumer Device Cardholder Verification Method : vérification du porteur sur le device — biométrie / code) et la protection : il ne remplace ni l’un ni l’autre.

Deux couples produits

Qui joue la carte · qui autorise le porteur

Ne pas confondre

SE = la carte (puce + secrets) · HCE = logiciel qui joue la carte · TEE = isolation CPU pour CDCVM (Consumer Device Cardholder Verification Method) — pas le canal RF. Un device combine souvent SE + TEE ou HCE + TEE.

Synthèse

Question clé · Apple / Google ne sont pas émetteurs

Comment, avec la saisie de la carte, mettent-ils un sans-contact interopérable ? Et où naissent les secrets ?

Point Réponse
Rôle Apple / Google Pas émetteurs · pas de copie du PAN · UX + présentation NFC (SE ou HCE)
Enrolment Saisie carte → TSP → émetteur autorise → token (DPAN)
Interop POS Même tuyau qu’une carte CL (14443 Type A + EMV) — le terminal voit une carte
AuthZ Scheme → TSP (détokenisation) → émetteur décide
Naissance des secrets Couple émetteur + TSP (cadré scheme) — génère / dérive UDK-AC · ni Apple ni Google ne les inventent
Apple (SE) Même naissance réseau → secret long injecté dans l’eSE · Apple = coffre
Android (HCE) Pas de coffre local digne → UDK-AC reste au TSP · phone = credentials courts
À retenir Secrets = émetteur / TSP · Apple/Google = NFC + coffre ou HCE · seule différence = où on range le secret long
