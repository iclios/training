4.3 · Wallets & confiance device

Architecture NFC mobile & wallets

Définition monétique

Qu’est-ce qu’un wallet de paiement ?

Application et stack device qui orchestrent l’enrolment, le provisioning d’un instrument (souvent un token), l’authentification porteur (biométrie / CDCVM) et la présentation NFC (card emulation) face au POS — sans remplacer l’émetteur ni la décision AuthZ.

SE, HCE, TEE : modèles de confiance — pas un classement « bon / mauvais ».

Confiance device

SE · HCE · TEE

1 · SE

Secure Element

Une puce dédiée qui est la carte sans contact face au POS (applet + secrets) — isolée de l’OS. Ce n’est pas l’app wallet qui « joue » la carte : c’est le coffre matériel qui répond aux APDU.

SE · où · quoi pour le tap

Puce dédiée · contenu · flux POS

2 · HCE

HCE · ce qui manque vs SE → nécessité du TSP

Host Card Emulation : le logiciel (OS / app) émule une carte sans contact face au POS (répond aux APDU comme une carte). Le TSP devient nécessaire pour faire ce que la SE faisait seule.

HCE a · Manque vs SE · TSP comble

Sans coffre matériel · le TSP comble le trou

3 · TEE

TEE · autorise le porteur · ≠ carte · ≠ SE

Trusted Execution Environment : zone isolée dans le processeur (SoC), séparée du rich OS. Elle n’est pas la carte sans contact et n’est pas la puce SE — elle autorise / protège (biométrie, CDCVM) pour que SE ou HCE puisse parler au POS.

TEE · où · ce qu’il fait · ce qu’il n’est pas

Partition CPU · preuve porteur · pas le canal RF

Ne pas confondre

SE = la carte (puce + secrets) · HCE = logiciel qui joue la carte · TEE = isolation CPU pour CDCVM / protection — pas le canal RF. Un device combine souvent TEE + SE, ou TEE + HCE.

Implémentations

SIM · eSE · HCE cloud

Trois façons de loger (ou non) le coffre SE — même question : où · qui gouverne · quoi pour un tap.

1 · SIM

SIM-based SE

Coffre sur la carte SIM / UICC — contrôle opérateur (MNO). Changer de SIM = changer de coffre.

Où ? · dans la SIM amovible

Slot SIM · SE à l’intérieur de la carte

Pour un tap CL, la SIM-SE contient

  • Applet card emulation (+ données EMV)
  • Token / DPAN et clés crypto
  • Contrôle opérateur — qui peut provisionner / suspendre

Au tap : POS ↔ NFC ↔ SE sur SIM · même logique SE, autre « boîte ».

2 · eSE

Embedded SE

Coffre soudé dans le téléphone — contrôle constructeur (OEM). Lié au device, pas à la SIM.

Où ? · puce soudée dans le device

Non amovible · reste si on change de SIM

Pour un tap CL, l’eSE contient

  • Applet card emulation · token · clés (coffre paiement)
  • Contrôle OEM — provisioning / lifecycle device
  • Souvent couplé à un TEE (biométrie / CDCVM)

Au tap : POS ↔ NFC ↔ eSE · CDCVM via TEE / Enclave.

3 · HCE cloud

HCE + cloud / TSP

Pas de coffre SE paiement sur le device. Secrets longs chez le TSP / cloud · tokens courts sur le phone (HCE, souvent + TEE).

Où ? · cloud + logiciel host

Long terme au TSP · court terme sur le device

Pour un tap CL, le modèle HCE cloud fournit

  • Stack HCE sur le device — répond aux APDU
  • Tokens / clés courts rechargeables
  • Vault TSP — secrets longs hors device
  • TEE — souvent CDCVM / protection locale

Au tap : POS ↔ NFC ↔ HCE · le cloud a préparé · pas de SE paiement.

Ne pas confondre

SIM et eSE = deux endroits pour une SE · HCE cloud = pas de SE, autre modèle de confiance (TSP).

Lifecycle token / chaîne TSP : J3 lifecycle · J3 architecture SI.

Rôle

Que retient le SI ?

Wallet apporte

  • UX, biométrie, orchestration device
  • Présentation NFC (card emulation)
  • Lien device ↔ token

Wallet ne remplace pas

  • Émetteur (AuthZ, compte)
  • Scheme / TSP (token network)
  • Clearing / settlement (J1)

Clarification

Ce que le wallet n’est pas

≠ L’émetteur

Le wallet orchestre — l’AuthZ reste côté banque / processeur.

≠ La tokenisation seule

Le token est le socle (J3) — le wallet y ajoute device, UX, NFC.

SE ≠ toujours « mieux »

HCE + gouvernance TSP peut être le modèle cible — comparer responsabilités.
