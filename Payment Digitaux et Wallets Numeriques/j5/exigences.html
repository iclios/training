Exigences SI transverses

Définition monétique

Qu’est-ce qu’une exigence SI omnicanale ?

Contrainte que la passerelle omnicanale doit tenir quelle que soit la porte (in-store · e-com · mobile · in-app) : parce que les canaux partagent le même cœur SI, pas quatre stacks.

Six axes transverses ; chaque exigence a un critère mesurable et un impact si elle est ratée. La traçabilité s’appuie sur le payment_id et le cycle Auth formel.

Évaluation

Exigence → critère · impact si défaillance

Grille d’évaluation : ce qu’on mesure, ce qui casse si on rate (ordres de grandeur pédagogiques).

Exigence Critère mesurable Impact en cas de défaillance
Disponibilité & résilience Cœur SI joignable pour toutes les portes ; SLA type 99,99 % (ordre de grandeur pédagogique) Rejet technique simultané sur tous les canaux · file · canal mort
Latence (p95) p95 passerelle < 500 ms pour in-store / NFC ; AuthZ bout-en-bout suivie séparément Timeout · abandon UX · file caisse / tap raté
Sécurité & conformité Chiffrement HSM ; vault PAN isolé ; PCI DSS + PCI PIN ; pas de PAN en clair hors vault Non-conformité · fraude · suspension d’acceptation
Auditabilité & traçabilité Journal immuable ; chaque événement rattaché à un payment_id (1 id / intention) ; AuthZ / Clear / Sett. rattachables Litige non rattachable · réconciliation manuelle · silos
Interopérabilité Standards EMVCo · ISO 20022 (selon rail) · EMV QR Specs Porte bloquée · intégration propriétaire · lock-in
Scalabilité Capacité pic multi-canaux (ex. flash e-com + flux magasins) sans saturation du cœur Saturation · files · dégradation latence / dispo

Repère : chaque exigence a un propriétaire module (gateway · fraude · journal / vault…) — sinon non pilotable en run.
