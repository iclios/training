Jour 5 · Omnicanal

5.1 · Cas d’usage & concepts

Paiement omnicanal

Définition monétique

Qu’est-ce que l’omnicanal ?

Capacité à accepter et traiter un paiement quel que soit le canal (magasin, web, mobile, in-app) via un backend de paiement unique, une orchestration multi-moyens et une expérience unifiée — sans silos produit juxtaposés.

Plusieurs moyens ≠ omnicanal si les flux, la vérité SI et les règles restent séparés par canal. Chaque transaction a une intention métier, un payment_id et un cycle Auth request → AuthZ → journal.

Canaux d’acceptation

Quatre cas d’usage

Quatre portes d’entrée. Même cœur SI ; l’intention métier décide si c’est le même payment_id ou un nouvel id.

In-store · E-com · Mobile · In-app

Quatre terrains · un même cœur SI

Canal Intention & moyens Cycle Auth
In-store Achat en magasin : tap NFC EMV Contactless ou QR affiché au TPE / caisse. Auth request POS → AuthZ → journal
E-commerce Paiement web Card-Not-Present (CNP) avec 3-D Secure et / ou token e-com (J3). AuthN 3DS puis AuthZ émetteur
Mobile Scan QR MPM / CPM via application bancaire ou wallet (J2). Payload QR → Auth request → AuthZ
In-app SDK / feuille wallet (Apple Pay, Google Pay) dans l’app commerçant (J4). Token device → AuthZ → journal

Parallèle

Multicanal vs omnicanal

Les deux exposent plusieurs canaux. La différence : silos juxtaposés (plusieurs journaux) ou 1 backend partagé (1 journal SI).

Schéma comparatif

Même surface client · architecture opposée

Dimension Multicanal Omnicanal
Présence Plusieurs canaux ouverts Plusieurs canaux ouverts
Architecture Silos juxtaposés (POS ≠ e-com ≠ app) 1 backend partagé · orchestration unique
Mémoire transactionnelle 3 journaux (une vérité par canal) 1 journal SI (une vérité transactionnelle)
payment_id Local au silo · pas de continuité 1 id / intention · portable entre canaux
Expérience Canal = parcours isolé Continuité (C&C, reprise mobile) si même intention

Repère : avoir web + magasin + app = multicanal. Les faire converger sur le même SI paiement = omnicanal.

Concepts piliers

Trois piliers de l’omnicanal

Backend unique · orchestration · UX unifiée — les trois s’appuient sur le même cycle Auth et le même payment_id par intention.

Backend · Orchestration · UX

Trois piliers · une vérité SI

Pilier 1

Single payment backend

Centralisation de la logique métier et unification de la mémoire de transaction : un seul journal de vérité SI pour toutes les portes — pas un export POS, un export e-com et un export app à recoller.

N portes · 1 journal SI

AuthZ → Clear → Sett. sous le même payment_id

Pilier 2

Orchestration multi-moyens

Routage intelligent, gestion des adaptateurs (carte / QR / wallet) et décision d’autorisation centralisée : une Auth request normalisée, une AuthZ, un statut — pas trois moteurs de règles concurrents.

Adaptateurs → cœur → AuthZ

Canaux → même plateforme → une décision

Les boîtes « Carte / QR / Wallet » = connecteurs dans le même SI, pas des backends concurrents.

Pilier 3

Expérience utilisateur unifiée

Continuité de parcours : click & collect, abandon web et reprise mobile, panier magasin lié à un ordre e-com. Le payment_id garantit le lien avec la même intention d’achat — pas un nouvel id à chaque porte.

Même intention · même payment_id

Changer de canal sans casser le paiement

Repère : le canal change ; l’intention et le payment_id ne changent que si c’est un nouvel achat.

Repère monétique

payment_id = une intention d’achat

Un payment_id identifie une intention d’achat : le « quoi payer » métier (panier / commande / ordre) — pas un canal, ni un geste technique (tap, scan, checkout).

Ce qui change (NFC, QR, carte, wallet) = le moyen / la porte. Le payment_id ne change que si c’est un nouvel achat.

Situation Intention payment_id
Achat spontané en caisse Nouvelle Nouvel id
Panier web, puis paiement Une Un id créé au checkout
Click & collect : même commande, payée / reprise en magasin La même Le même id
Deux achats le même jour (web + magasin) Deux Deux ids
Abandon web, reprise mobile du même panier La même Le même id

En une phrase : le payment_id suit l’achat que le client veut finaliser — ce n’est pas un nouvel id à chaque fois qu’il change de canal.

Exemple concret · Click & Collect

Même intention · même payment_id · deux portes

Cas : Léa commande un casque à 89 € sur le site (retrait en magasin). Le SI crée payment_id = ORD-7841. L’après-midi, en magasin, le vendeur scanne le bon / Léa tape NFC : l’AuthZ et le journal portent toujours ORD-7841 — ce n’est pas un second paiement inventé par le POS.

Étape Multicanal (silos) Omnicanal (même SI)
① Web · commande casque Export / journal e-com : id WEB-9912 (stack web seule) Journal SI : ORD-7841
② Magasin · retrait / paiement Export / journal POS : nouvel id POS-448 — le TPE ne « voit » pas WEB-9912 Même ligne : ORD-7841 (reprise d’intention)
Conséquence Deux dossiers à recoller (export e-com + export POS) ; risque double débit / litige / « déjà payé web » vs « à encaisser en caisse » Une intention, un id, une timeline ; AuthZ et clôture sur la même vérité SI

Différence : en multicanal, changer de canal = souvent changer de mémoire (nouvel id, autre export). En omnicanal, changer de canal = continuer la même intention sous le même payment_id.
