1.4 · Flux transactionnel

Autorisation

Définition monétique

Qu’est-ce qu’une autorisation ?

Procédure par laquelle une demande d’accord est transmise à l’émetteur (issuer) — ou à un système agissant pour son compte — afin qu’il accepte ou refuse une opération présentée sur un moyen de paiement carte, et renvoie une réponse exploitable par la chaîne d’acceptation.

« Agissant pour son compte »

La décision reste celle de l’émetteur. En face, ce peut être son host, un processeur d’émission, un stand-in (émetteur injoignable), ou un centre délégué — toujours au nom de l’émetteur, pas du commerçant ni du scheme.

Une autorisation, c’est un dialogue : une demande part, une réponse revient.

Échange de messages

Demande / réponse

Au sens monétique, une autorisation = un aller (demande) et un retour (réponse) sur la même chaîne — du porteur jusqu’à l’émetteur, puis le chemin inverse.

Chaîne de l’autorisation

Porteur · Acceptation · Acquéreur / PSP · Réseau · Émetteur

Pont J3 : en modèle classique le PAN est dans la demande ; la tokenisation le remplacera sans changer cette logique monétique.

Cas stand-in

Émetteur injoignable — même chaîne, décision déléguée

Même parcours. Si l’émetteur est injoignable, un stand-in décide au niveau réseau / processeur — la réponse redescend ensuite hop par hop jusqu’au porteur.

Le stand-in agit pour l’émetteur ; le message redescend toute la chaîne jusqu’au porteur.

Émetteur

Que décide le centre d’autorisation ?

C’est le cœur métier de l’autorisation : l’émetteur (ou son système) dit oui ou non à cette opération.

Moyen de paiement

  • Statut : actif, opposé, expiré, bloqué…
  • Produit / compte associé (débit, crédit…)
  • Validité du support et données de la demande

Capacité & plafonds

  • Disponible / autorisation de découvert
  • Plafonds (jour, opération, canal…)
  • Règles produit (pays, MCC, type d’opération)

Cohérence de l’opération

  • Montant, devise, commerçant / MCC
  • Canal (proximité, e-com, récurrent…)
  • Géographie, horodatage, séquence

Risque & fraude

  • Scoring / règles anti-fraude
  • Signaux device / comportement
  • Exigence d’AuthN porteur selon le contexte → bloc Authentification

Résultat renvoyé

Approve = accord (+ code d’autorisation) · Decline = refus (+ codes motif). En stand-in, mêmes types de réponse, avec un jeu de règles souvent plus restrictif.

Ancrage

Cas pratiques

Après la définition — pour faire parler la salle, pas pour remplacer le cadre monétique.

Cas 1 — Accord

  • Demande acheminée jusqu’à l’émetteur
  • Contrôles OK
  • Réponse d’approbation + code d’autorisation

Faire dire : la décision est chez l’émetteur.

Cas 2 — Refus métier

  • Même chemin message
  • L’émetteur refuse (disponible, opposition, risque…)
  • C’est une réponse d’autorisation, pas un « bug »

Cas 3 — Échec technique

  • Timeout, indispo réseau ou host émetteur
  • Pas de décision métier claire dans les délais
  • Diagnostic ≠ decline « fonds insuffisants »

Cas 4 — Pré-autorisation (optionnel)

  • Accord sur un montant estimé / à compléter
  • Toujours une autorisation au sens monétique
  • Cycle métier différent (complétion / capture)

À ouvrir si le public acquiring / PSP le demande.

Clarification

Ce que l’autorisation n’est pas

≠ Authentification (CVM / AuthN)

AuthN = légitimité du porteur · Auth = accord de l’émetteur sur l’opération. Souvent liées (étape 4 vs 6), toujours distinctes.

Check de fin de bloc

  • Définition monétique restituée (demande + réponse + émetteur)
  • Auth localisée dans le cycle EMV (≠ AuthN / CVM)
  • Au moins un cas (accord / refus métier / technique) maîtrisé
  • Pont PAN dans le flux d’auth évoqué sans dériver sur le token
