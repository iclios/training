1.4 · Flux transactionnel

Autorisation

Définition monétique

Qu’est-ce qu’une autorisation ?

Procédure par laquelle une demande d’accord est transmise à l’émetteur (issuer) — ou à un système agissant pour son compte — afin qu’il accepte ou refuse une opération présentée sur un moyen de paiement carte, et renvoie une réponse exploitable par la chaîne d’acceptation.

  • Message de demande — montant, données du moyen de paiement, commerçant, type d’opération…
  • Routage — acquéreur (éventuellement PSP / gateway) puis réseau (scheme)
  • Traitement émetteur — contrôles métier, risque, statut du support…
  • Message de réponse — approbation ou refus + codes / références (dont code d’autorisation si accord)

Caractéristiques

Échange online typique · décideur = émetteur · objet = accord sur l’opération — pas la compensation ni le règlement · support = messages normalisés (famille type ISO 8583 / formats scheme).

Cycle monétique

Où se situe l’autorisation ?

Autorisation → Authentification* → Clearing → Settlement

*L’authentification du porteur est souvent liée ou préalable selon le canal — bloc suivant. Ici on isole la décision d’accord.

L’autorisation répond à

  • « L’émetteur accepte-t-il cette opération ? »

Clearing / settlement répondent à

  • « Comment les banques se compensent-elles et se règlent-elles ensuite ? »

Échange de messages

Demande / réponse

Au sens monétique, une autorisation = un aller (demande) et un retour (réponse) jusqu’à la chaîne d’acceptation.

Chaîne de l’autorisation

Acceptation · Acquéreur / PSP · Réseau · Émetteur

Pont J3 : en modèle classique le PAN est dans la demande ; la tokenisation le remplacera sans changer cette logique monétique.

Émetteur

Que décide le centre d’autorisation ?

  • Statut du moyen de paiement (actif, opposé, expiré…)
  • Capacité à réaliser l’opération (plafonds, disponible…)
  • Cohérence de l’opération (montant, MCC, canal, géographie…)
  • Règles de risque / fraude
  • Exigences d’authentification du porteur selon le contexte → bloc Authentification

Vocabulaire à figer

Approve = autorisation accordée · Decline = autorisation refusée · Code d’autorisation = référence d’accord côté émetteur (quand accord).

Ancrage

Cas pratiques

Après la définition — pour faire parler la salle, pas pour remplacer le cadre monétique.

Cas 1 — Accord

  • Demande acheminée jusqu’à l’émetteur
  • Contrôles OK
  • Réponse d’approbation + code d’autorisation

Faire dire : la décision est chez l’émetteur.

Cas 2 — Refus métier

  • Même chemin message
  • L’émetteur refuse (disponible, opposition, risque…)
  • C’est une réponse d’autorisation, pas un « bug »

Cas 3 — Échec technique

  • Timeout, indispo réseau ou host émetteur
  • Pas de décision métier claire dans les délais
  • Diagnostic ≠ decline « fonds insuffisants »

Cas 4 — Pré-autorisation (optionnel)

  • Accord sur un montant estimé / à compléter
  • Toujours une autorisation au sens monétique
  • Cycle métier différent (complétion / capture)

À ouvrir si le public acquiring / PSP le demande.

Clarification

Ce que l’autorisation n’est pas

≠ Clearing

Pas encore la compensation des opérations entre établissements via le réseau.

≠ Settlement

Pas encore le règlement des positions financières entre banques.

≠ Authentification

AuthN = légitimité du porteur · AuthZ monétique = accord de l’émetteur sur l’opération. Souvent liées, toujours distinctes.

Notes formateur — questions SI
  • Quel composant est votre centre d’autorisation / host issuing ?
  • Où tracez-vous demande vs réponse (codes, délais, timeouts) ?
  • Qui porte le diagnostic decline métier vs incident technique ?

Livrable mental : reformuler la définition monétique sans anecdote magasin, puis illustrer avec un cas.

Check de fin de bloc

  • Définition monétique restituée (demande + réponse + émetteur)
  • Auth ≠ clearing ≠ settlement
  • Au moins un cas (accord / refus métier / technique) maîtrisé
  • Pont PAN dans le flux d’auth évoqué sans dériver sur le token
Sources normes / specs — à affiner : messages d’autorisation (ISO 8583 / formats scheme), règles réseau, EMV online, PCI sur les données du flux d’auth.
