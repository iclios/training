2.5 · Architecture SI & flux

Architecture SI QR

Définition

Qu’est-ce que l’architecture SI QR ?

Les composants qui permettent de générer, lire et autoriser un paiement initié par QR — du téléphone jusqu’au SI banque ou au SI wallet (provider).

Le QR change l’initiation — pas Auth → Clearing → Settlement (J1). D’abord les éléments SI, la séquence, le cadrage MPM / CPM, puis trois cas pour voir où ça change.

Éléments SI

Où tournent les briques

Carte des SI — le QR engine s’accroche à l’acteur qui encode ou décode. Le PSP n’est pas « une boîte unique » : c’est un rôle configuré — côté commerçant (acceptation) ou côté client (app banque / wallet). SI banque et SI wallet : même rôle AuthZ, deux maisons possibles.

Application · Backend · PSP · SI banque · SI wallet

PSP = rôle (commerçant ou client) · + moteur QR

Flux

Séquence du paiement QR

Même enchaînement pour les trois cas : génération → scan & validation → autorisation. La confirmation est le retour OK / KO (sens inverse) — pas un 4ᵉ hop avant. Ensuite : clearing / settlement (J1).

Aller · Auth → Retour · confirmation

La confirmation remonte le chemin — elle ne continue pas à droite

Cadrage

MPM · CPM — qui présente, qui route ?

Deux modes EMVCo (specs distinctes) : MPM et CPM. Pull / push = vocabulaire de cours (pas EMVCo) : pull ≈ marchand présente, push ≈ payeur présente. Ce qui change : qui affiche, qui scanne, le payload, et quel PSP est sur le chemin Auth (rôle configuré). Scan ≠ AuthZ.

MPM · CPM (pull / push = cours)

Présentation · payload · quel PSP · AuthZ

MPM : PSP client acquiert le flux. Le réseau contrôle l’ID acquéreur marchand (valeur QR) — il ne le route pas comme hop Auth. Auth → émetteur. CPM : PSP commerçant acquiert le flux. Pull / push = cours, pas EMVCo.

Moyen de paiement — quels identifiants ?

MPM vs CPM · banque vs wallet

Spec CPM EMVCo = données type chip (ADF, cryptogramme…). Closed-loop wallet = IDs provider. Carte tokenisée dans un wallet → AuthZ chez l’émetteur de la carte.

Cas 1 · MPM dynamique (tag 01 = 12) · « pull »

La caisse affiche un QR

Le payeur scanne avec son app. Auth via PSP côté client → réseau → émetteur. La caisse n’est pas sur ce chemin : elle apprend le résultat par notification (webhook / push PSP) grâce à la référence trx mise dans le QR à la génération.

MPM · dynamique

Tag 01 = 12 — réseau contrôle ID acquéreur · route → émetteur

Cas 2 · MPM statique (tag 01 = 11) · « pull »

Sticker magasin

Même sens MPM : QR déjà imprimé. Le réseau contrôle l’ID acquéreur marchand du sticker — pas un hop « vers l’acquéreur ». Auth → émetteur.

MPM · statique

Tag 01 = 11 — réseau contrôle ID acquéreur · route → émetteur

Cas 3 · CPM · « push »

Le payeur présente un QR

La caisse scanne. Spec EMVCo CPM : credentials type carte / chip (ADF, token ou PAN, cryptogramme…). Le PSP commerçant mappe ça en message Auth → (réseau) → SI de l’émetteur. Wallet closed-loop : IDs provider → SI wallet.

CPM

Credentials type carte · PSP commerçant · AuthZ émetteur

Synthèse

Payload · quel PSP · AuthZ

Cas Payload QR Chemin Auth AuthZ / suite
MPM · 12 (« pull ») IDs marchand · montant souvent PSP client → réseau (contrôle ID acquéreur) Route Auth → émetteur
MPM · 11 (« pull ») IDs marchand (fixes) PSP client → réseau (contrôle ID acquéreur) Route Auth → émetteur
CPM (« push ») Credentials type carte/chip PSP commerçant acquiert le flux SI émetteur (ou wallet closed-loop)

Contrôler l’ID acquéreur = préparer le règlement : trouver la banque du marchand, puis créditer le commerçant (client final) après coup. Ce n’est pas un hop Auth vers l’acquéreur.
